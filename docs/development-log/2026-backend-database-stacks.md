# 2026— 백엔드 프레임워크·데이터베이스 비교 학습

## 데이터베이스 유형

### 관계형 데이터베이스 (RDBMS)

- 데이터를 테이블과 관계로 표현하고 SQL로 조회·수정합니다.
- 스키마, 제약 조건, 트랜잭션을 활용해 관계가 분명하고 정합성이 중요한 데이터를 다룰 수 있습니다.
- ACID는 원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 지속성(Durability)을 설명하는 트랜잭션 특성입니다. 실제 보장 수준은 DB 설정과 격리 수준, 사용 방식에 영향을 받습니다.
- 관계형 DB가 금융에 흔히 쓰이는 것은 중요한 선택 근거 중 하나지만, 특정 제품이나 유형 하나만으로 안정성·정확성이 보장되는 것은 아닙니다. 스키마와 트랜잭션 설계, 백업, 장애 대응, 보안 운영이 함께 필요합니다.

| 데이터베이스 | 특징과 고려할 점 | 검토할 수 있는 용도 |
|---|---|---|
| MySQL / MariaDB | 널리 사용되는 관계형 DB이며 호스팅과 자료가 풍부합니다. 두 제품은 역사적으로 밀접하지만 현재 기능·호환성과 지원 정책을 각각 확인해야 합니다. | 일반 웹, 블로그, 게시판, 쇼핑몰 |
| PostgreSQL | SQL과 트랜잭션을 기반으로 다양한 데이터 유형과 확장 기능을 제공합니다. 기능이 풍부한 만큼 데이터 모델과 운영 설정을 이해해야 합니다. | 복잡한 관계 데이터, 핀테크, 신규 서비스, 분석 기능이 필요한 앱 |
| Oracle Database / Microsoft SQL Server | 상용 제품으로 기업 지원과 조직 내 운영 경험을 활용할 수 있습니다. 라이선스·지원 비용과 공급자별 기능·이식성을 검토합니다. | 대기업, 공공, 기존 금융·업무 시스템 |

### 비관계형 데이터베이스와 검색·관리 서비스

NoSQL은 한 가지 저장 방식이 아니라 문서, 키-값, wide-column, 그래프 등 여러 데이터 모델을 포함하는 범주입니다. 모든 NoSQL 데이터베이스가 트랜잭션이나 정합성을 지원하지 않는다고 일반화하지 말고, 제품별 기능과 일관성 모델을 확인합니다.

| 기술 / 유형 | 특징과 고려할 점 | 검토할 수 있는 용도 |
|---|---|---|
| MongoDB (문서형) | 문서 형태로 데이터를 모델링하며 스키마 변화가 잦은 데이터에 유연할 수 있습니다. 관계·인덱스·트랜잭션 요구에 맞춰 데이터 모델을 설계합니다. | 문서 중심 콘텐츠, 빠른 제품 실험, 일부 이벤트 데이터 |
| Redis (키-값·인메모리) | 메모리 기반 자료구조와 빠른 접근으로 캐시, 세션, 임시 상태 등에 활용됩니다. 영속성·메모리 한도·축출 정책을 확인하고, 원본 데이터 저장소와 역할을 구분합니다. | 캐시, 세션, 랭킹, 실시간 상태 |
| Cassandra (wide-column) | 분산 환경의 대규모 쓰기·조회 패턴에 맞춰 모델링합니다. 질의 패턴을 먼저 정하는 데이터 모델과 운영 복잡도를 고려합니다. | 대규모 이벤트·로그·시계열 성격의 데이터 |
| DynamoDB (관리형 키-값/문서형) | AWS 관리형 서비스로 파티션 키와 접근 패턴 중심 설계가 중요합니다. 비용, 용량 모드, 제한과 AWS 종속성을 검토합니다. | AWS 기반 서비스의 예측 가능한 키 조회 |
| Elasticsearch (검색·분석 엔진) | 전문 검색과 분석 조회에 강점이 있습니다. 보통 트랜잭션 원본 DB를 대체하기보다 검색 인덱스로 두고 동기화·재색인·일관성을 설계합니다. | 전문 검색, 로그 분석 |
| Firebase (BaaS 제품군) | 인증·데이터·호스팅 등 관리형 기능으로 빠르게 앱을 구성할 수 있습니다. 제품별 데이터 모델, 보안 규칙, 비용과 공급자 종속성을 검토합니다. | 프로토타입, 소규모 앱, 관리형 백엔드가 적합한 서비스 |

### RDBMS와 NoSQL 선택

| 비교 관점 | 관계형 DB | NoSQL 계열 |
|---|---|---|
| 데이터 모델 | 테이블과 관계 | 문서·키-값·wide-column·그래프 등 제품별 모델 |
| 스키마 | 명시적 구조와 제약 조건을 활용하기 쉬움 | 유연한 모델을 제공하는 제품이 있으나 설계 규칙이 없어지는 것은 아님 |
| 트랜잭션·일관성 | 강한 트랜잭션과 제약 조건이 필요한 업무에 적합한 경우가 많음 | 지원 수준과 일관성 보장은 제품·설정별로 다름 |
| 확장 방식 | 수직 확장과 복제·분할 등 여러 방식을 조합 | 수평 확장에 적합하도록 설계된 제품이 있지만 운영·질의 제약이 따름 |
| 예시 용도 | 결제, 주문, 정형 업무 데이터 | 캐시, 세션, 문서, 대규모 분산 접근 패턴 |

많은 서비스는 관계형 DB를 주요 원본 저장소로 두고 Redis를 캐시나 임시 상태 저장에 사용합니다. 캐시의 값은 원본 데이터와 달라질 수 있으므로 만료·무효화와 장애 시 동작도 설계해야 합니다. “RDB 또는 NoSQL 중 하나”가 아니라 각 저장소의 역할을 분리해 함께 쓰는 선택도 가능합니다.

## 프로젝트별 스택 조합을 검토하는 관점

| 프로젝트 유형 | 검토할 수 있는 구성 | 중요하게 볼 점 |
|---|---|---|
| 은행·금융 업무 | Java/Spring 또는 조직 표준 백엔드, 관계형 DB, React/Angular 등 | 권한, 감사 추적, 트랜잭션, 규정, 장기 지원, 기존 시스템 연동 |
| 증권·실시간 거래 | 성능 민감 엔진과 일반 업무 API를 분리하고, 관계형 DB·캐시·WebSocket 등을 용도별 검토 | 실제 지연 시간 측정, 데이터 정확성, 장애 복구와 규제. 특정 언어 하나가 전체 시스템을 대표하지 않음 |
| 게임 | Unity/C# 또는 Unreal/C++ 클라이언트, 별도 게임 서버와 관계형 DB·캐시 | 플랫폼, 동시 접속, 실시간 상태, 계정·결제와 랭킹 데이터의 차이 |
| 게시판·커뮤니티 | Laravel, Django, Node.js 등과 MySQL/PostgreSQL | 콘텐츠·댓글·검색·관리자 기능, 개발 속도와 팀 경험 |
| 블로그·콘텐츠 | WordPress 같은 CMS 또는 Next.js/Django와 콘텐츠 저장소 | 편집자 경험, SEO, 콘텐츠 관리, 운영 방식 |
| 이커머스 | 규모와 팀에 맞는 백엔드, 관계형 DB, 필요에 따라 캐시와 외부 결제 서비스 | 주문·재고·결제 트랜잭션, 중복 요청, 가격·재고 정합성, 트래픽 대응 |
| 스타트업 MVP | Next.js/TypeScript, Django, Rails 등 팀이 빠르게 배포할 수 있는 구성 | 검증 속도, 적은 인력으로 운영 가능성, 향후 변경 비용 |
| 실시간 채팅·협업 | Node.js/TypeScript 또는 Go, WebSocket, 필요에 따라 Redis·DB | 연결 수와 메시지 전달 보장, 재연결·순서, 확장 및 관측성 |
| AI·데이터 서비스 | Python/FastAPI 등과 관계형 DB 또는 특화 저장소 | 모델·GPU 운영, 추론 지연, 데이터 파이프라인, API 경계와 비용 |

이 표는 업계에서 볼 수 있는 조합의 예시이지 특정 도메인의 필수 선택을 뜻하지 않습니다. 요구사항, 데이터 정합성, 규제·보안, 팀 숙련도, 기존 자산, 채용·운영 가능성과 총비용을 함께 평가합니다.

## 핵심 비교와 학습 순서

- 언어·프런트엔드·백엔드·데이터베이스는 서로 다른 층의 선택이며, 모든 층을 같은 회사나 언어의 제품으로 맞출 필요는 없습니다.
- 초보자는 HTML/CSS/JavaScript, Git, UI 프레임워크, API와 SQL, 배포 순으로 작은 프로젝트를 만들어 보며 경험을 넓힐 수 있습니다.
- 한 언어와 도구를 먼저 실제 프로젝트에 사용하고, 필요가 생길 때 다른 스택을 비교하면 기술 선택의 이유를 구체적으로 익히기 좋습니다.
- 최신 버전이나 성능 수치는 변하므로 공식 문서와 프로젝트별 측정을 기준으로 삼습니다.
