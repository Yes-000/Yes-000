# 2026 — API·인증·알림·데이터·애니메이션 학습

> 이 기록은 REST API, Next.js 서버 처리, 메시징 연동, 인증·인가, QR 본인 확인, 데이터 모델링과 애니메이션 구현에 관해 학습한 내용을 정리합니다.

## REST API 설계

- URL은 리소스 중심으로 설계하고, 동작은 HTTP method로 표현하는 방식을 익혔습니다. 예를 들어 조회·생성·수정 작업을 `/getUser`, `/createOrder` 같은 동사형이 아니라 `/users`, `/orders`처럼 리소스와 method의 조합으로 표현합니다.
- 복수형 경로와 계층 구조를 일관되게 사용합니다. 예: `/orders/{orderId}/items`.
- 일반적인 method 용도는 `GET` 조회, `POST` 생성 또는 명령, `PUT` 전체 교체, `PATCH` 부분 수정, `DELETE` 삭제입니다. 멱등성은 method 이름만으로 보장되는 것이 아니라 서버 구현과 요청 의미에 따릅니다.
- 상태 코드는 성공 시 `200`, `201`, `204`, 요청·인증·권한 오류에 `400`, `401`, `403`, `404`, 중복·경합에 `409`, 요청 제한에 `429`, 예상하지 못한 서버 오류에 `500` 계열을 구분해 사용합니다.
- 오류 응답의 필드(`code`, `message`, 필요 시 `details`, `requestId`)를 일관되게 유지하면 클라이엔트가 오류를 처리하기 쉽습니다.
- 필터와 정렬은 query parameter로 표현하고, 정렬 표기법은 한 가지로 통일합니다. 작은 목록은 `page`와 `limit`을, 대규모·변경이 잦은 목록은 정렬 키와 커서 기반 페이지네이션을 고려합니다.
- 주문 취소처럼 별도의 기록이 중요한 작업은 상태 변경으로 표현할지, `/orders/{orderId}/cancellations` 같은 하위 리소스로 표현할지 도메인과 이력 요구에 따라 결정합니다.

## Next.js Route Handler와 Server Action

- 클라이언트에서 호출 가능한 서버 경계에서는 Zod 등으로 입력을 검증한 뒤 업무 로직을 실행합니다.
- 서버 전용 환경 변수는 Route Handler나 Server Action 등 서버에서만 접근하며, 클라이언트로 전달하지 않습니다.
- 외부 API 호출은 네트워크 오류, 타임아웃, 재시도 가능 여부, 안전한 로그와 실패 처리를 함께 설계합니다. 재시도는 중복 실행의 영향을 확인하고 적용합니다.

## 카카오·채널톡 연동과 알림 처리

- 카카오 로그인은 계정 인증·연결, 알림톡은 거래 과정의 안내 메시지, 친구톡은 마케팅 동의와 수신 거부가 중요한 홍보 메시지, 채널톡은 상담 대화에 적합합니다.
- 로그인 제공자의 사용자 식별자를 계정 연결에 사용하고 이메일만으로 동일인을 단정하지 않습니다.
- 알림 발송은 상태 변경 요청 안에서 외부 API까지 동기 호출하기보다, 상태 변경과 outbox 이벤트를 DB transaction으로 기록하고 worker가 제공자 API를 호출하도록 설계할 수 있습니다.
- 메시지 이벤트에는 신청 생성·확약·완료처럼 목적을 명확히 표현하고, idempotency key 등으로 중복 발송을 방지합니다.
- 발송 대기(`queued`), 제공자 접수(`sent`), 도착 확인(`delivered`), 실패(`failed`), 발송 생략(`skipped`)은 서로 다른 상태입니다. 제공자 응답만으로 실제 도착을 단정하지 않습니다.
- 업무 알림과 마케팅 메시지는 수신자 범위, 동의와 수신 거부 규칙을 분리합니다. 수신자는 브라우저 입력을 신뢰하지 않고 서버가 역할과 소속에 따라 결정합니다.
- 메시지 본문은 업무상 필요한 최소 정보만 포함하고 민감정보를 넣지 않습니다. API 키와 발신 번호는 서버 전용 환경 변수로 보관하며 로그에 출력하지 않습니다.
- 대체 채널을 사용할 때에는 동일 이벤트가 여러 채널에서 중복 발송되지 않도록 발송 상태와 fallback 정책을 함께 설계합니다.

## 인증과 인가

- **인증(Authentication)**은 사용자가 누구인지 확인하고, **인가(Authorization)**는 그 사용자가 무엇을 할 수 있는지 확인합니다.
- 프런트엔드에서 메뉴나 버튼을 숨기는 것은 UX 보조일 뿐입니다. API는 요청마다 서버에서 역할과 대상 데이터 범위를 확인하고, 정책에 따라 `401` 또는 `403`을 반환합니다.
- 세션이나 토큰의 종류와 무관하게 최종 권한 확인은 서버에서 수행합니다.

## PASS 본인 확인과 QR 고객 입력

- 소셜 로그인의 계정 인증과 PASS 본인 확인은 목적이 다릅니다. 소셜 계정에 로그인했다는 사실만으로 거래 당사자의 실명·명의 확인이 완료된 것은 아닙니다.
- 서버에서 거래와 연결된 QR 세션을 만들고, 예측하기 어려운 일회성 토큰과 만료·상태를 관리합니다. 상태는 예를 들어 `active`, `in_progress`, `expired`, `replaced`, `completed`처럼 분리할 수 있습니다.
- 인증 사업자의 결과는 브라우저 값만 신뢰하지 않고 서버 간 검증을 거치며, 결과가 올바른 QR 세션과 거래에 연결되었는지 확인한 후 다음 단계로 진행합니다.
- 최종 제출은 중복되지 않도록 idempotency와 DB transaction을 고려합니다.
- QR URL에 주민등록번호나 전화번호를 넣지 않고 무작위 토큰만 사용합니다. 가능하면 원문 토큰 대신 해시를 저장하고, 민감한 원문 정보는 로그와 디버깅 화면에 노출하지 않습니다.
- 파트너 화면에는 고객 원문 정보 대신 진행 상태만 반환합니다. 임시 저장이 필요하면 수집 최소화, 짧은 보관 기간, 암호화와 파기 정책을 함께 검토합니다.
- 만료·교체·다른 기기 진행·인증 실패·미성년자·재접속 등 예외 흐름과 안내 문구를 미리 설계합니다.
- 인증된 전화번호를 계정 키로 쓰는 방식은 간단하지만 번호 재할당과 다중 번호 문제가 있습니다. 더 강한 동일인 식별자가 필요하면 도입 비용, 법적 기준과 운영 책임을 함께 검토해야 합니다.

### QR 본인 확인 테스트 관점

- 성공·실패·취소·타임아웃과 중복 콜백
- 다른 세션이나 거래에 묶인 인증 결과 차단
- 만료·교체·완료된 QR 재접속
- 새로고침·뒤로가기 후 중복 제출 방지
- 파트너 화면에서 고객 민감정보를 볼 수 없는지
- 인증 후 브라우저를 닫았다가 다시 열었을 때 상태가 정책대로 복구되는지

## 데이터 모델·검증·표현

- 서버 DTO와 프런트엔드 ViewModel은 목적이 다를 수 있으므로 변환 계층을 둘 수 있습니다.
- 날짜와 시간은 ISO-8601 형식으로 주고받고, 표시와 시간대 변환 책임을 정합니다.
- 금액은 단위와 소수점 정책을 먼저 정합니다. 예를 들어 원 단위 정수로 전달하고 프런트에서 표시용 문자열로 포맷할 수 있습니다.
- 입력 검증, 개인정보 최소화, 권한 범위, 이력 기록은 API와 UI를 함께 포함하는 데이터 흐름으로 설계합니다.

## 애니메이션 구현 방식

- **CSS transition**은 상태 변화에 따른 hover, 활성화, 열기·닫기 등에 간단하고 가볍게 사용할 수 있지만 복잡한 타임라인 제어에는 제한이 있습니다.
- **CSS keyframes**는 반복이나 단계적 연출에 적합하고, 단순한 애니메이션은 JavaScript 없이 구현할 수 있습니다.
- **SVG 애니메이션**은 아이콘·로고·선 그리기 같은 벡터 표현에 유용하지만 복잡한 그래픽은 파일이 커질 수 있습니다.
- **GIF**는 재생이 단순하지만 용량과 제어 측면에서 불리할 수 있습니다. 긴 영상형 애니메이션은 WebM/MP4가 더 효율적일 수 있고, UI 상태 제어는 제한적입니다.
- **Lottie**는 구간·속도 제어에 유용하지만 재생 라이브러리와 번들 비용을 고려해야 합니다.
- **Canvas/WebGL 또는 JavaScript 애니메이션**은 상호작용·파티클·복잡한 그래픽에 적합할 수 있지만 구현 난이도와 CPU/GPU 사용량을 고려합니다.
- 대부분의 UI 모션은 `transform`과 `opacity`를 우선 검토합니다. `width`, `height`, `top`, `left` 등 레이아웃에 영향을 주는 속성은 성능 영향을 확인하고 사용합니다.
- 가장 적합한 방식은 애니메이션 길이, 상호작용, 접근성, 디바이스 성능, 번들 크기와 실제 파일 크기를 기준으로 선택합니다.

## 배운 점

- REST API는 경로·HTTP method·상태 코드·오류 응답을 일관되게 설계해야 클라이언트와 서버의 계약이 분명해집니다.
- 외부 메시징은 DB 상태 변경과 분리해 실패와 재시도, 중복 발송을 다룰 수 있도록 설계합니다.
- 로그인, 실명 확인, 업무 권한은 서로 다른 보안 개념이므로 하나의 성공 여부로 뭉뚱그리지 않습니다.
- QR 흐름은 토큰 수명, 거래 연결, 재접속, 중복 제출, 개인정보 보관을 함께 다뤄야 합니다.
- 날짜·금액·DTO는 전송 규칙과 화면 표시 규칙을 나누어 정의하면 해석 차이를 줄일 수 있습니다.
- 애니메이션은 효과의 복잡도와 상호작용에 맞는 기술을 선택하고, 용량·성능·접근성도 함께 고려합니다.
