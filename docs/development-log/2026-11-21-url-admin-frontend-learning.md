# 2026-11-21 — URL·관리자 데이터 흐름·프런트엔드 구현 학습

> 이 기록은 URL 설계, 신청 데이터의 저장·조회·권한 관리, TypeScript와 React 구현, Tailwind CSS 사용에 관해 학습한 내용을 정리합니다. 예시는 개념을 설명하기 위한 것으로 실제 프로젝트의 구조와 보안 정책에 맞게 조정합니다.

## URL 설계: Path variable과 Query parameter

- **Path variable**은 어떤 리소스를 다루는지 식별하는 데 적합합니다. 예: `/partner/materials/123`, `/partners/{partnerId}`. 목록·상세 경로와 상하위 리소스 관계를 표현할 때 사용합니다.
- **Query parameter**는 같은 리소스 컬렉션을 어떤 조건으로 조회하거나 표현할지 나타냅니다. 예: `/partner/materials?status=published&page=2&sort=createdAt.desc`. 검색, 필터, 정렬, 페이지네이션 등에 사용합니다.
- `materials`처럼 도메인 리소스는 명사형 경로로 표현하고, 상세 식별자는 경로에 두며 필터는 쿼리에 둡니다.
- `view`가 그리드·리스트 같은 표시 옵션이면 `?view=grid`처럼 쿼리로, 저장되는 뷰 템플릿 엔티티라면 `/partner/views/{viewId}`처럼 리소스 경로로 표현할 수 있습니다.
- `navigation`은 UI 네비게이션 자체를 가리키는지 메뉴 설정 기능을 가리키는지 명확히 해, 목적에 맞는 경로 이름을 선택합니다.

## 신청 데이터의 저장·조회·처리 흐름

### 전체 흐름

1. 웹 폼에서 신청 정보를 제출합니다.
2. 서버가 입력을 검증하고 정규화합니다.
3. 서버가 데이터베이스에 신청 본문과 필요한 이력을 저장합니다.
4. 권한을 확인한 관리자가 페이징·필터·정렬을 이용해 목록을 조회합니다.
5. 허용된 관리자가 상세 내용을 확인하고 상태·담당자·메모를 처리합니다.
6. 필요하면 알림, CRM 등 후속 작업을 연결합니다.

### 쓰기와 조회

- 클라이언트가 데이터베이스에 직접 쓰기보다 서버 API를 통해 제출하도록 설계할 수 있습니다. 서버는 필수값, 길이, 포맷을 검증하고 공백 제거 등 정규화를 수행합니다.
- 중복 제출과 스팸에 대응할 때는 요청 제한, honeypot, 중복 정책 등 적절한 방식을 검토합니다.
- 전화번호·이메일 등 개인정보가 로그나 오류 메시지에 원문으로 남지 않도록 마스킹과 로그 정책을 고려합니다.
- 데이터 모델은 신청 본문, 관리자 메모, 상태·담당자 변경 이벤트처럼 성격이 다른 정보를 분리할 수 있습니다. 예를 들어 신청 테이블, 메모 테이블, 감사 이벤트를 별도로 두는 방식입니다.
- 관리자 목록은 상태·분류·기간·담당자 필터, 검색·정렬·페이지네이션을 제공할 수 있습니다. 상세에는 필요한 원문과 이력, 처리 기능을 표시합니다.

## 역할과 데이터 접근 경계

- 관리자 화면의 접근 제어는 메뉴나 버튼을 숨기는 데 그치지 않습니다. 목록·상세·변경 API마다 서버가 인증과 역할 기반 인가를 최종 확인해야 합니다.
- 사용자가 보낸 신청 ID, `branchId` 같은 쿼리 값은 권한 증명이 아닙니다. 서버는 인증된 사용자로부터 소속과 허용 범위를 계산하고, 그 범위 안에서 조회해야 합니다.
- 역할별 조회 범위와 허용 필드는 명시적으로 분리합니다. 운영 관리자, 지점장, 팀장, 파트너에게 같은 신청 데이터 전체를 무조건 노출하지 않습니다.
- 목록 API는 필요한 최소 필드만 반환하고, 민감한 식별번호·카드·계좌 원문은 목록과 로그에서 제외합니다. 상세 접근도 업무상 필요한 최소 범위를 따릅니다.
- 공통 접근 정책 함수와 테스트를 두면 역할 규칙이 화면별로 복제되어 달라지는 위험을 줄일 수 있습니다.

테스트에서는 자기 범위의 조회 성공, 다른 소속 ID 직접 조회 차단, 타인의 메모 변경 차단, 정지 계정의 접근 차단, 역할·상태 변경 감사 기록 등을 확인합니다. 접근 불가 리소스에서 `403` 또는 리소스 존재 여부를 감추는 `404` 중 무엇을 반환할지는 서비스 정책에 맞춥니다.

## TypeScript와 안전한 파싱

- API 응답의 원본 타입과 화면에서 사용하기 좋은 ViewModel을 분리하면 데이터 변환과 UI 표현을 독립적으로 다룰 수 있습니다.
- `type`을 선호하거나 컴포넌트 Props 타입 이름을 `Props`로 통일하는 것은 팀 컨벤션으로 정할 수 있습니다. `any`는 가능한 피하고 구체적인 타입을 사용합니다.
- 구분자 문자열을 파싱할 때 특정 구분자가 항상 존재하거나 split 결과 길이가 고정이라고 가정하지 않습니다.
- 첫 번째 `-`만 구분자로 사용하고 나머지 문자열은 그대로 보존하는 예시는 다음과 같습니다.

```tsx
type ParsedTabId = { section: string; slug: string };

export const parseTabId = (tabId: string): ParsedTabId => {
  const dashIndex = tabId.indexOf('-');

  if (dashIndex === -1) {
    return { section: '', slug: tabId };
  }

  return {
    section: tabId.slice(0, dashIndex),
    slug: tabId.slice(dashIndex + 1),
  };
};
```

구분자가 없거나 맨 앞에 있는 값, 구분자가 여러 개인 값도 테스트해 의도한 기본값과 원본 보존을 확인합니다. `_` 기반 규칙처럼 다른 형식을 사용할 때도 누락된 배열 요소에 기본값을 지정하고 입력 범위를 테스트합니다.

## React 스크롤 이벤트와 상태 최적화

- 스크롤 이벤트처럼 자주 발생하는 이벤트에서는 DOM을 통해 다음 상태를 계산하고, 이전 값과 실질적으로 다를 때만 새 상태를 반환할 수 있습니다.
- 값이 같으면 기존 상태 객체를 반환해 불필요한 업데이트 가능성을 줄입니다.
- 이벤트 빈도가 실제 성능 문제가 될 때는 `requestAnimationFrame`이나 throttle을 검토하되, 먼저 측정하고 필요한 경우에 적용합니다.

```tsx
type TabEdge = { top: boolean; bottom: boolean };

const updateTabEdge = (next: TabEdge) => {
  setTabEdge((prev) =>
    prev.top === next.top && prev.bottom === next.bottom ? prev : next,
  );
};
```

## Tailwind CSS 클래스 구성

- 조건부 클래스나 호출자가 전달한 클래스와 기본 클래스를 병합할 때 `cn()` 같은 유틸리티를 사용할 수 있습니다. 정적인 클래스만 나열하는 경우에는 꼭 필요하지 않습니다.
- `clsx`는 조건부 클래스 결합에, `tailwind-merge`는 충돌하는 Tailwind 유틸리티를 정리하는 데 활용됩니다.
- 클래스 순서를 위치·오프셋·레이아웃·간격·크기·패딩·테두리·색상 등의 팀 규칙으로 정하면 읽기와 리뷰가 쉬워질 수 있습니다. 다만 순서 규칙은 스타일의 동작 자체보다 코드 일관성을 위한 컨벤션입니다.

## 배운 점

- Path와 query는 각각 리소스 식별과 조회·표현 조건을 맡도록 구분하면 URL의 의도가 명확해집니다.
- 신청 데이터 처리에서는 검증, 개인정보 최소화, 역할별 범위, 이력 관리가 하나의 흐름으로 설계되어야 합니다.
- 브라우저에서 보이는 권한 UI는 편의를 위한 것이고, 데이터 접근은 서버에서 요청마다 검증해야 합니다.
- 외부 문자열은 누락·추가 구분자·빈 값이 있을 수 있으므로 방어적으로 파싱하고 테스트합니다.
- 빈번한 상태 업데이트는 실제 값이 변했는지 확인하고, 최적화는 측정한 병목을 기준으로 적용합니다.
- 팀의 타입·컴포넌트·CSS 규칙은 유용한 일관성 도구이지만 모든 프로젝트에 그대로 적용되는 언어 규칙은 아닙니다.
