# 2026 — 개발 환경과 프런트엔드 기초 학습

> 이 기록은 개발 환경을 구성하고 기능을 구현하며 익힌 도구와 개념을 정리합니다. 외부 참고 자료로 [Claude artifact](https://claude.ai/artifact/J1EYHB3gPsvEWCkS3PC88h#page-dcb81aee8d83)를 함께 남깁니다.

## 오늘 학습하고 적용한 내용

### Git 저장소와 작업 흐름

- `git clone`으로 원격 저장소를 내려받고, `cd`로 프로젝트 디렉터리와 파일 경로를 이동·확인하는 흐름을 익혔습니다.
- 기능별 브랜치를 만들어 작업하고, 변경 사항을 스테이징한 뒤 커밋하고 원격 브랜치에 푸시하는 과정을 연습했습니다.
- 작업 브랜치에서 Pull Request를 만들어 `main`에 반영하고, 병합 후 자동 배포가 실행되는 흐름을 익혔습니다.
- `git stash`, `git stash list`, `git stash apply`, `git stash pop`으로 커밋 전 변경 사항을 임시 보관하고 복원하는 방법을 배웠습니다. `apply`는 보관 항목을 남기고, `pop`은 적용 후 해당 항목을 제거합니다.

```bash
git clone <repository-url>
cd <project-directory>
git checkout -b feature/login
pnpm install
pnpm dev

git add <files>
git commit -m "feat: add login"
git push -u origin feature/login
```

프로젝트에 따라 `pnpm build`와 `pnpm start`로 빌드 및 실행을 확인합니다. 스크립트 이름과 작업 브랜치의 병합 방식은 저장소 설정에 맞춰 확인합니다.

### 패키지 설치와 개발 서버

- `pnpm install`로 프로젝트에 정의된 의존성을 설치합니다.
- `pnpm add <package>`는 런타임 의존성을, `pnpm add -D <package>`는 개발 의존성을 추가합니다.
- 설치 정보는 `package.json`과 lockfile에 기록되며 패키지는 `node_modules`에서 사용됩니다.
- `pnpm dev`, `pnpm build`, `pnpm start`는 각각 개발 서버 실행, 빌드, 빌드 결과 실행에 쓰입니다. 실제 동작은 프로젝트의 스크립트 정의를 확인해야 합니다.

### Figma와 디자인 참고 자료

- Figma MCP를 연결해 디자인 맥락을 참고하고, 지정된 프로젝트 경로에 화면을 구현하는 작업 흐름을 익혔습니다.
- 웹사이트를 참고 자료로 전달할 수 있는지, 실제 서비스의 디자인을 Figma로 가져올 수 있는지 먼저 확인하는 방법을 배웠습니다.
- 외부 디자인을 참고할 때는 접근 권한, 가져오기 도구의 지원 범위, 라이선스와 사용 허가를 확인하고, 결과물을 그대로 복제하기보다 프로젝트의 요구와 디자인 규칙에 맞춰 적용합니다.

### 프런트엔드 구조와 데이터 흐름

- 브라우저에서 보이는 `web`과 `admin`, 요청을 처리하는 API/server, 데이터를 보관하는 DB와 Storage의 역할을 구분했습니다.
- 데이터 요청은 개념적으로 `Browser (Frontend) → API (Server) → DB (Backend)`의 흐름을 따릅니다. API는 요청을 검증하고 필요한 데이터를 조회하거나 저장하는 경계입니다.
- `route`는 주소와 화면·동작을 연결하는 경로입니다.
- `component`는 UI와 동작을 재사용 가능한 단위로 구성합니다. 고정된 UI와, `children` 등으로 내용이나 배치를 바꿀 수 있는 유연한 UI의 장단점을 비교했습니다.
- `children`은 컴포넌트의 여는 태그와 닫는 태그 사이에 전달되는 내용을 받아 화면을 조합하는 방법입니다. `chip`은 상태나 짧은 분류 정보를 표시하는 작은 UI 요소로 학습했습니다.
- 프런트엔드 개발자 문서와 프로젝트 문서를 찾아 사용법과 제약을 확인하는 습관을 익혔습니다.

### Fetch와 페이지네이션

- `fetch`는 주소(endpoint)에 요청을 보내 선택된 데이터나 응답을 가져오는 기본 방법입니다. 어떤 정보를 조회할지, 요청 조건과 SQL/query가 어느 계층에서 처리되는지 구분해서 이해했습니다.
- 목록 데이터가 많을 때 한 번에 전부 가져오지 않고 나눠 조회하는 페이지네이션 개념을 학습했습니다.
- **오프셋 페이지네이션**은 `limit`과 `offset` 또는 페이지 번호로 위치를 지정합니다. 구현이 직관적이고 임의 페이지 이동에 편리하지만, 데이터가 앞에 추가·삭제되면 페이지 사이에 중복이나 누락이 생길 수 있으며 큰 offset은 조회 비용이 커질 수 있습니다.
- **커서 페이지네이션**은 정렬 기준의 마지막 값이나 고유 식별자를 다음 요청의 기준으로 사용합니다. 데이터가 계속 추가되는 목록에서 안정적이고 큰 목록을 이어 읽기에 적합하지만, 임의 페이지 이동과 전체 페이지 수 표시는 상대적으로 어렵습니다.
- 어떤 방식을 쓸지는 목록의 정렬, 데이터 변경 빈도, 사용자가 필요한 이동 방식과 성능 요구를 고려해 결정합니다. 정렬 조건은 일관되고 동률을 구분할 고유 키를 포함해야 합니다.

### 환경별 설정과 Supabase

- `local-local`, `dev-dev`, `prod-prod`처럼 웹 앱과 데이터 서비스가 같은 환경을 바라보도록 구분하는 원칙을 익혔습니다. 로컬 웹 서버를 로컬 Supabase에 연결할 때는 CLI 상태와 환경 변수의 URL·키가 같은 프로젝트를 가리키는지 확인해야 합니다.
- URL은 서비스 주소이고, 키는 해당 서비스에서 허용된 접근 범위를 결정하는 인증 정보입니다. API 주소에는 필요한 경로(endpoint)가 붙을 수 있습니다.
- 브라우저에서 쓰는 공개 키와 서버 전용 비밀 키는 구분해야 합니다. `VITE_` 접두사가 붙은 변수는 브라우저 번들에 포함될 수 있으므로 `SUPABASE_SERVICE_ROLE_KEY` 같은 서비스 역할 키를 넣어서는 안 됩니다. 서비스 역할 키는 서버의 안전한 환경 변수에만 두고 공개 저장소·로그·클라이언트 응답에 노출하지 않습니다.

```dotenv
# 브라우저에서 사용 가능한 공개 설정의 예시
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_ANON_KEY=<public-anon-key>

# 서버 전용 설정의 예시 — 클라이언트 번들에 노출하지 않음
SUPABASE_URL=https://<project>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<server-only-secret>
```

실제 변수 이름은 프레임워크와 프로젝트 설정을 따릅니다. 키 값은 문서나 코드에 기록하지 않고, 개발·운영 환경별로 분리해 관리합니다.

## 배운 점

- 저장소를 내려받는 것부터 브랜치 생성, 변경 기록, PR, 병합과 배포까지의 흐름을 이해하면 기능 구현과 팀 협업을 함께 진행할 수 있습니다.
- 프런트엔드는 화면만이 아니라 경로, 컴포넌트 조합, API 경계, 데이터 조회 방식과 환경 설정을 함께 고려해야 합니다.
- 유연한 컴포넌트는 재사용성이 높고 고정형 컴포넌트는 사용 규칙이 단순합니다. 어느 쪽이 나은지는 변형 요구와 실제 사용처를 기준으로 선택합니다.
- 페이지네이션은 화면의 페이지 번호만 정하는 일이 아니라 정렬·동시 데이터 변경·조회 비용을 함께 고려하는 데이터 조회 설계입니다.
- 환경 변수는 이름만 맞추는 것이 아니라 환경과 권한 범위까지 맞춰야 하며, 비밀 키를 브라우저에 노출하지 않아야 합니다.
