## 1. 모노레포와 프레임워크 분리

### 오늘 한 일

- `pnpm workspace`와 Turborepo를 이용해 여러 앱과 공용 패키지를 하나의 저장소로 관리했습니다.
- 공개 웹은 Next.js, 운영자 관리 화면은 Vite와 React로 나눴습니다.
- 디자인 시스템과 데이터베이스 타입을 공용 패키지로 분리했습니다.

### 해결한 문제

- 앱마다 같은 버튼과 타입을 복사하면 변경 시 누락이 발생합니다.
- 공개 웹과 사내 도구는 사용자 범위와 SEO 요구가 다릅니다.
- 새 앱이 늘 때마다 빌드와 배포 설정이 커질 수 있습니다.

### 왜 이렇게 했는가

- Next.js는 공개 페이지의 서버 렌더링과 검색 노출에 유리했습니다.
- Vite는 로그인 뒤 사용되는 운영 도구에 필요한 개발 속도와 가벼운 SPA 구조에 적합했습니다.
- 공통 부품은 모노레포에서 공유해 한 번의 변경으로 여러 앱을 맞출 수 있게 했습니다.

### 선택한 대안과 이유

| 방식 | 장점 | 선택하지 않은 이유 |
|---|---|---|
| 모든 앱을 Next.js로 통일 | 구조가 같고 배포가 한곳에 모임 | 운영자 앱까지 서버 렌더링 복잡도를 떠안아 요구와 어긋남 |
| 모든 앱을 Vite로 통일 | 개발과 빌드가 가벼움 | 공개 서비스의 SEO와 초기 렌더링 이점을 잃음 |
| Next.js + Vite 모노레포 | 각 앱 요구에 맞추고 공용 코드는 공유 | 앱별 설정과 빌드 경로를 관리해야 함 |

### 배운 점

- 프레임워크 통일보다 각 앱의 요구를 기준으로 선택하는 것이 중요합니다.
- 공유는 코드를 줄여주지만 서버리스·번들링 경계까지 고려해야 합니다.
- 모노레포의 규칙은 캐시와 변경 범위를 함께 설계해야 효율을 냅니다.

## 2. 폴더 구조와 앱 셸

### 오늘 한 일

- 주소 라우팅은 `app/`, 공통 껍데기는 `shells/`, 실제 화면은 `views/`에 두는 역할 분리를 적용했습니다.
- 부업 카테고리 이동 시 헤더 상태가 유지되도록 페이지 레이아웃 밖으로 앱 셸을 올렸습니다.
- 화면에서만 쓰는 컴포넌트는 가까운 폴더에 두고 여러 앱이 공유할 때만 상위로 올렸습니다.

### 해결한 문제

- 페이지를 옮길 때마다 헤더가 다시 생성되어 위치 인디케이터가 초기화됐습니다.
- 주소 변경과 화면 내용이 한 파일에 혼합되면 서로 다른 변경을 한 곳에서 처리해야 했습니다.
- 긴 표나 텍스트가 있으면 레이아웃이 가로로 늘어나는 문제가 있었습니다.

### 해결 방법

- 헤더를 라우트 그룹 레이아웃인 셸로 끌어올려 페이지 전환에도 리마운트되지 않게 했습니다.
- 주소 담당과 실제 화면 담당을 분리했습니다.
- 플렉스 콘텐츠에 최소 폭 제한을 풀어 남은 화면을 정확히 채우도록 했습니다.

### 배운 점

- 앱 셸 패턴은 어느 UI가 페이지 경계를 넘어 살아남아야 하는지 결정하는 설계입니다.
- 컴포넌트를 전역 폴더에 미리 모으기보다 실제 사용 범위를 기준으로 둬야 합니다.
- URL, 레이아웃, 화면 데이터의 책임이 같은 파일에 섞이지 않게 해야 합니다.

## 3. 인증과 권한 경계

### 오늘 한 일

- 일반 사용자와 파트너는 소셜 로그인과 자체 세션 흐름을 사용했습니다.
- 운영자와 다른 역할은 각 앱의 인증과 권한을 분리했습니다.
- 세션과 로그인 수단을 역할별로 나누고 서버에서 계정 상태를 다시 확인했습니다.

### 해결한 문제

- 로그인 여부만 보면 정지된 계정이나 역할 변경 계정을 즉시 막을 수 없습니다.
- 브라우저가 보낸 ID나 필터는 권한이 아니라 화면 편의를 위한 값일 수 있습니다.
- 회원 탈퇴와 접수·지급 기록이 서로 같은 수명으로 처리되면 업무 근거가 사라질 수 있습니다.

### 해결 방법

- 일반 사용자 세션과 운영자 인증을 분리했습니다.
- 보호 대상 요청마다 계정 상태와 실제 접근 범위를 서버에서 다시 확인했습니다.
- 테이블 권한과 데이터베이스 접근 규칙을 역할별로 제한했습니다.
- 민감한 토큰·키·개인정보 열람 절차는 공개 문서에서 제외하고 `(보안)`으로 관리했습니다.

### 알고 남긴 위험과 더 나은 선택

- 정지 상태가 로그인 쿠키에만 반영되면 쿠키를 가진 사람이 API를 직접 호출할 수 있습니다.
- 역할 확인을 프런트에서만 하면 주소를 직접 호출했을 때 권한이 무너집니다.
- 여러 역할을 처음부터 하나의 범용 Viewer로 만들면 단순해질 수 있지만, 역할이 많은 지금은 서버에서 역할별 범위를 명시하는 방식이 더 안전했습니다.

### 확인한 테스트 방향

- 사용 중지 계정과 재설정 후 예전 세션 거부
- 로그인 시도 제한이 web과 상담사 앱 사이에서 의도한 방식으로 동작하는지 확인
- 남의 접수는 상세 조회와 민감 열람 이전에 차단되는지 확인
- 탈퇴한 회원의 개인정보와 업무 기록 수명을 분리해 확인

## 4. 데이터베이스와 마이그레이션

### 오늘 한 일

- 데이터베이스 구조 변경을 SQL 마이그레이션 파일로 남겼습니다.
- 직접 콘솔에서 임의로 표를 고치는 대신 변경 기록을 깃과 배포 절차에 연결했습니다.
- 민감 데이터는 넓은 테이블 권한을 열지 않고 보안 함수와 뷰로 제한했습니다.

### 해결한 문제

- DB를 직접 손으로 바꾸면 코드가 기대하는 구조와 실제 구조가 어긋날 수 있습니다.
- 넓은 UPDATE 권한을 주면 운영자 콘솔이나 잘못된 클라이언트에서 다른 칸까지 변경할 수 있습니다.
- 데이터베이스 함수와 화면 검증을 따로 두면 한쪽만 수정되어 불일치가 생깁니다.

### 해결 방법

- 마이그레이션 파일에서 표·컬럼·함수·권한을 함께 기록했습니다.
- 쓰기는 가능한 곳을 제한된 함수로 열고, 읽기도 뷰와 칼럼 권한으로 나눴습니다.
- 확약·확정·계약 수정의 검증은 우선 하나의 서버 또는 데이터베이스 경계를 기준으로 삼았습니다.

### 배운 점

- 데이터베이스 변경은 애플리케이션 배포와 호환 순서를 함께 고려해야 합니다.
- 구버전 앱이 남아 있을 수 있으므로 새 구분을 사용할 때는 이전 동작과의 호환을 명시해야 합니다.
- 상태 칸을 여러 곳에 복제하면 갱신 시 불일치가 발생하므로 사건 표나 원본 행의 존재로 단계가 결정되도록 했습니다.

## 5. 휴대폰·인터넷·유심 영업과 견적

### 오늘 한 일

- 휴대폰은 기종·통신사·요금제·할인·보험·제휴카드를 가진 견적 구조로 만들었습니다.
- 인터넷은 속도별 TV 조합과 설치비를 가진 별도 상품 구조로 만들었습니다.
- 유심은 휴대폰 요금제 흐름을 재사용하되 별도 접수 정보로 관리했습니다.

### 해결한 문제

- 공통 지원금과 선택약정은 결제 방식이 달라 단순 합계로 계산할 수 없습니다.
- 비어 있는 할인과 실제 0원은 같은 값처럼 처리하면 잘못된 견적이 생깁니다.
- 인터넷 속도 표기 차이로 요금 조합을 찾지 못하는 문제가 있었습니다.
- 화면마다 계산식을 복사하면 할인 규칙이 조금씩 달라질 수 있습니다.

### 해결 방법

- 휴대폰 견적의 공통 지원금, 약정 할인, 월 납부금 규칙을 공용 계산으로 통합했습니다.
- 비어 있는 값과 실제 0원은 구분했습니다.
- 속도와 요금 조합의 저장·조회 키를 같은 규칙으로 맞췄습니다.
- 제휴카드와 결합 할인도 견적에 포함해 계약 전후 금액이 어긋나지 않게 했습니다.

### 변경 이력과 검증

- 휴대폰 목록과 상세, 요금제 선택, 카드 할인과 신규 가입 흐름을 여러 차례로 나눠 구현했습니다.
- 인터넷 상품과 TV 조합, 설치비, 결합 할인과 고객 대상 저장을 확장했습니다.
- 유심은 요금제 통합과 상품군별 필터를 통해 휴대폰 흐름을 재사용했습니다.
- 할부와 선납, 선택약정과 카드 할인 같은 경우를 테스트로 고정했습니다.

### 남은 위험과 개선 방향

- 화면이 계산한 금액을 그대로 전송하는 방식은 DB가 받은 값을 완전히 재검증하지 못할 수 있습니다.
- 자유 텍스트로 입력된 요금제 혜택은 데이터가 바뀌면 해석이 틀릴 수 있습니다.
- 금액과 할인 유형을 구조화된 필드로 올리고 서버가 최종 일치를 검사하는 방향이 필요합니다.

## 6. QR 세션과 고객 최종 제출

### 오늘 한 일

- 파트너가 QR을 발급하고 고객이 휴대전화로 여러 단계의 정보를 입력하도록 만들었습니다.
- 새로고침과 재접속을 고려해 진행 상태를 서버 세션으로 관리했습니다.
- 고객이 최종 제출하면 계약과 접수 상태가 바로 생성되도록 바꿨습니다.

### 해결한 문제

- 브라우저 상태만으로 진행하면 새로고침이나 기기 변경에서 입력이 유실됐습니다.
- 파트너가 '신청서 제출하기'를 누르지 않으면 계약과 접수 정보가 사라질 수 있었습니다.
- QR을 다시 만들면 이전 접수가 잘못 취소되거나 다른 세션에 영향을 줄 수 있었습니다.

### 해결 방법

- QR 발급 시 계약 초안을 세션에 저장했습니다. 고객 제출 시 초안을 계약 테이블로 옮긴 뒤 비우도록 했습니다.
- 세션이 없으면 최종 제출이 접수를 생성하지 않도록 했고 배포 호환 구간은 예외 흐름을 두었습니다.
- 완료 화면은 접수 완료로 가는 확인과 QR 재생성을 구분했습니다.
- 재생성 시 앞 접수를 휴지통으로 옮기고, 이미 확약·확정된 접수는 막았습니다.

### 운용상 선택과 단점

- 계약 초안은 파트너가 화면을 닫아도 접수가 이어지도록 하는 장점이 있습니다.
- 그 대신 제출 전 고객과 제3자 정보가 서버에 머뭅니다. 보관 기한과 파기 배치를 설계했습니다.
- 이미 발송된 접수 문자와 취소 문자는 서로 되돌릴 수 없습니다. 재생성 시 취소 문자를 별도로 보냈습니다.
- 해당 변경 전 고객 제출이 접수되지 않은 건수는 사전에 계측하지 못해 정확한 개선 효과를 수치로 남기지 못했습니다.

### 배운 점

- 고객 제출을 최종 접수 시점으로 두면 파트너 브라우저의 생존 여부와 무관하게 접수가 성립합니다.
- 세션 재발급과 취소는 별도 동작이므로 이전 신청의 범위를 명시적으로 제한해야 합니다.
- 복사본과 원본 보관 정책을 사전에 정하지 않으면 삭제·재생성·탈퇴에서 불일치가 발생합니다.

## 7. 개인정보와 민감 제출 정보

### 오늘 한 일

- 일반 계약 정보와 주민번호·결제수단 같은 민감 제출 정보를 분리했습니다.
- 민감정보 열람은 기록을 먼저 남긴 뒤 복호화와 반환을 진행하도록 했습니다.
- 열람 기록 실패 시 값을 보여주지 않도록 했습니다.

### 해결한 문제

- 민감값을 목록에 포함하면 화면을 그리기 위해 모든 고객의 개인정보가 브라우저로 내려갈 수 있습니다.
- 열람 기록이 없으면 누가 언제 정보를 봤는지 나중에 확인할 수 없습니다.
- 탈퇴나 파기 요청이 일반 기록과 민감 기록에 모두 적용되지 않으면 개인정보가 남습니다.

### 해결 방법

- 상세 뷰는 기본적으로 식별자와 업무 정보만 읽고 민감정보는 별도 열람 경로로 분리했습니다.
- 열람 기록과 복호화 순서를 강제했습니다.
- 민감값 수정은 브라우저가 직접 쓰는 테이블을 우회하도록 서버 함수로 처리했습니다.
- 암호화 키와 정확한 열람 절차는 `(보안)`으로 표시했습니다.

### 배운 점

- 목록은 개인정보를 덜어내고 상세에서 필요한 값만 여는 것이 기본입니다.
- 열람 기록은 값의 복호화 성공 여부와 함께 고려해야 합니다.
- 기록을 남기고 실제 열람이 실패하는 경우를 구분해야 모호한 감사 기록을 줄일 수 있습니다.

## 8. 어드민 확약·진행·실적 확정

### 오늘 한 일

- 통신 접수의 확약과 실적 확정 단계를 분리했습니다.
- 어드민은 표를 읽기만 하고 쓰기는 데이터베이스 함수를 통해 처리했습니다.
- 진행 중은 별도의 사건 기록으로 관리하고 완료 시 기존 실적 확정 함수를 호출했습니다.

### 해결한 문제

- 초기에는 실적 행을 만드는 경로가 없어 모든 파트너의 실적이 누락됐습니다.
- 확약과 실적 확정이 같은 시점으로 처리되면 배송·개통 진행 중인 건을 표현할 수 없습니다.
- 브라우저가 확약 시각을 보내면 기기 시각에 따라 귀속과 집계가 달라졌습니다.

### 해결 방법

- 실적 행 존재 여부를 확정 여부의 기준으로 사용했습니다.
- 진행 시작 기록과 실적 확정 기록을 분리했습니다.
- 확약과 취소, 휴지통 상태를 함수가 재확인하도록 했습니다.
- 서버 시각을 기준으로 하고, 동시에 눌렀을 때는 원본 행을 멱등하게 반환했습니다.

### 알고 남긴 장단점

- 실적 행 하나로 확정 여부를 판단하면 상태 칸을 두 곳에 복제하지 않습니다.
- 중간 단계가 더 늘어날 가능성이 있으면 처음부터 사건 표를 두는 편이 좋습니다.
- 기존 어드민이 남아 있는 구간에서는 DB 배포를 먼저 해야 확약과 실적 확정 의미가 어긋나지 않습니다.

### 처음부터 고정한 테스트

- 같은 건을 두 번 확약해도 실적은 한 건
- 완료되지 않은 세션, 취소 또는 휴지통 건, 이미 확정된 건의 진행 거절
- 어드민 권한은 진행 기록 조회만 허용
- 취소 후 재승인된 건의 상태 판단

## 9. 휴지통·비고·메모장

### 오늘 한 일

- 신청 행을 실제로 삭제하지 않고 휴지통 시각을 별도 칸으로 관리했습니다.
- 삭제된 신청이 파트너 활동과 등급 집계에서 제외되도록 뷰를 만들었습니다.
- 비고와 상세 메모장을 같은 데이터 원본에서 읽고 쓰도록 통합했습니다.

### 해결한 문제

- 신청 행에는 계약, 신청서, 실적, 리베이트가 매달려 있어 하드 삭제하면 참조가 깨질 수 있습니다.
- 어드민 목록에서만 숨기면 파트너의 최근 활동과 집계에 삭제 건이 남았습니다.
- 목록 비고와 상세 메모장을 별도로 관리하면 같은 대상의 값이 어긋납니다.

### 해결 방법

- 휴지통 시각을 두고 삭제를 복구 가능한 상태 전환으로 바꿨습니다.
- 삭제 신청을 제외한 파트너 집계 뷰를 만든 뒤 등급과 합계를 그 뷰로 읽게 했습니다.
- 이미 지급된 금액은 삭제 건에서 제외하더라도 기록에 남도록 예외를 설계했습니다.
- 비고와 메모장은 같은 대상과 값을 읽고 쓰며 충돌 시 다시 불러오도록 했습니다.

### 배운 점

- 삭제는 화면에서 한 상태만 숨기는 일이 아니라 모든 집계와 보존 기록에 영향을 줍니다.
- 이미 나간 지급액과 진행 중인 실적은 같은 삭제 규칙으로 한꺼번에 없애면 안 됩니다.
- 공용 메모는 읽기와 쓰기를 같은 원본으로 묶어야 상태가 어긋나지 않습니다.

## 10. 계약 수정과 수정 이력

### 오늘 한 일

- 휴대폰·유심·인터넷 계약을 데이터베이스 함수에서 검증하고 수정하도록 했습니다.
- 변경된 칸만 수정 이력에 남겼습니다.
- 회원과 민감 신청서 정보는 일반 계약 수정과 분리했습니다.

### 해결한 문제

- 어드민이 계약 표를 직접 수정하면 화면 검증과 DB 검증이 갈릴 수 있습니다.
- 요금제 이름만 바꾸고 기준 식별자를 바꾸지 않으면 리베이트 기준이 옛 요금제로 계산될 수 있습니다.
- 확정된 실적을 수정할 수 없도록 막았던 규칙을 어드민과 상담사가 다른 방식으로 해석할 수 있었습니다.

### 해결 방법

- 세션 행을 잠그고 취소·휴지통 상태를 확인한 뒤 계약을 수정했습니다.
- 요금제 식별자와 이름을 함께 받았습니다.
- 기존 값과 새 값의 차이만 이력에 남겼습니다.
- 민감정보는 암호화·복호화 경계를 서버에 두고 평문을 로그와 응답에 싣지 않았습니다.
- 어드민만 기존 확정 건 수정 권한을 받고 상담사 창구는 계속 제한했습니다.

### 알고 남긴 부작용

- 승인된 리베이트 금액은 그대로인데 마진이나 영업 현황이 계약을 다시 읽어 어긋나 보일 수 있습니다.
- 화면이 계산한 금액을 전송하는 방식은 콘솔에서 함수를 직접 호출했을 때 틀린 합계를 저장할 수 있습니다.
- 기존 함수를 그대로 복사해 권한만 바꾸면 diff가 커졌지만 누락을 줄일 수 있었습니다.

### 개선 방향

- 계약 계산식을 어드민과 상담사 공용 패키지로 공유했습니다.
- 다음 단계로 DB에서 수신 합계와 계산식 일치를 검증하는 것이 필요합니다.
- 취소된 회원의 이력과 민감값은 탈퇴 정책에 따라 함께 정리해야 합니다.

## 11. 추가 상품 접수

### 오늘 한 일

- 이미 접수된 고객에 휴대폰·유심·인터넷 상품을 더해 묶음 접수를 만들었습니다.
- 새 세션은 접수번호를 받고 고객과 파트너 정보는 기준 접수에서 물려받았습니다.
- 계약 없는 접수에는 빈 계약을 만든 뒤 기존 계약 수정 규칙으로 채웠습니다.

### 해결한 문제

- 고객 신청서를 복사할 때 암호문과 보관 기한까지 정확히 물려받아야 했습니다.
- 추가 접수에 다른 고객을 지정하면 기존 접수의 고객까지 바뀌는 문제가 있었습니다.
- 상품군별로 다른 검증을 두면 추가 접수와 일반 접수의 규칙이 갈렸습니다.

### 해결 방법

- 새 접수의 계약은 빈 행부터 만들고 기존 수정 함수를 사용해 검증했습니다.
- 묶음의 맨 처음 접수를 기준으로 관계를 잡았습니다.
- 가족 구성원 변경은 상담원이 잠그고 원본 접수와 추가 접수의 고객을 분리했습니다.
- 고객 입력은 계약 저장보다 먼저 같은 트랜잭션에서 검증했습니다.

### 확인한 테스트

- 세 상품군 추가와 신청서 복사
- 암호문과 보관 기한 복사
- 거절 케이스 뒤 남는 행이 없어야 함
- 뿌리와 자식 어느 쪽에서 열어도 같은 묶음
- 삭제·취소·미완료 접수 제외
- 예전 고객 수정 함수가 첫 접수까지 바꾸는 실패 케이스 회귀 차단

## 12. 지점장·상담사·운영자 업무 앱

### 오늘 한 일

- 지점장과 팀장용 관리 앱을 만들었습니다.
- 상담사 전용 계정과 담당 접수 범위를 분리했습니다.
- 어드민, 지점장 앱, 상담사 앱의 단계와 배지를 공통 의미로 맞췄습니다.

### 해결한 문제

- 지점장과 상담사별로 같은 접수의 고객 범위를 다르게 계산하면 남의 접수를 볼 수 있습니다.
- 계정을 하나만 바꾸면 다른 앱의 권한이 즉시 닫히지 않을 수 있습니다.
- 담당자 메모와 어드민 비고를 같은 표로 쓰면 작성자가 누구인지 가릴 수 없습니다.

### 해결 방법

- 지점장 앱은 요청마다 소속과 직급을 서버에서 다시 읽었습니다.
- 상담사 계정은 일반 회원과 분리하고 담당 파트너와 건별 배정을 기준으로 접수 범위를 계산했습니다.
- 상담사 메모와 어드민 비고는 서로 다른 표로 분리했습니다.
- 민감정보 열람은 담당 확인, 기록 저장, 복호화 순서를 강제했습니다.

### 지점장 앱에서 배운 점

- 총괄매니저가 지점장 역할을 대체하면 조회 코드는 재사용할 수 있지만 비고와 알림 동작까지 따라올 수 있습니다.
- 역할이 늘 가능성이 있으면 고정 직급 목록보다 역할과 범위 정책을 분리하는 편이 낫습니다.
- 소속을 쿠키에 보관해도 권한이 아니라 사용자의 선호로 취급해야 합니다.

### 상담사 앱에서 배운 점

- 같은 규칙을 어드민과 상담사 함수가 따로 구현하면 금액 계산과 이력이 달라집니다.
- 상담사 함수가 어드민 함수를 감싸고 담당자 확인을 앞뒤에 두는 방식은 규칙을 재사용할 수 있지만 이력 작성자를 별도로 채워야 합니다.
- 상세 모달과 서버 액션을 운영 빌드로 확인하지 않으면 개발 서버에서 보이지 않는 오류를 놓칠 수 있습니다.

### 운영 장애 사례

- `'use server'` 파일에서 타입을 다시 내보내면 프로덕션 빌드에서 서버 액션이 로드될 때 실패했습니다.
- 다음 메모장이나 민감 열람 액션이 상세 화면에서 전부 500으로 멈췄습니다.
- 재내보내기를 제거하고 타입을 사용하는 쪽에 직접 import하도록 고친 뒤 서버 액션을 빌드와 실행으로 확인했습니다.

## 13. 대출(정책자금) 영업

### 오늘 한 일

- 통신 접수와 같은 세션 기반 QR 흐름 위에 대출 고객 입력을 만들었습니다.
- 사업장, 매출, 신용등급, 필요 자금, 이용 대출, 연락처 순서로 정보를 받았습니다.
- 어드민과 상담사는 접수 대기, 전달 대기, 승인 대기, 실적 확정 단계로 나눴습니다.

### 해결한 문제

- 통신과 대출의 본인 확인은 재사용했지만 이후 입력 항목과 제출 결과가 달랐습니다.
- 대출은 확약이 없으므로 통신 접수의 진행 단계와 그대로 맞출 수 없습니다.
- 엑셀 내보내기와 상담사 배정 과정에서 전달 대기와 진행 기록이 어긋날 수 있었습니다.

### 해결 방법

- 대출 세션은 통신 세션과 같은 기반을 쓰되 상품군을 대출로 구분했습니다.
- 대출 신청서와 성격이 다른 통신 신청서를 별도 표로 저장했습니다.
- 실적 확정은 실적 행 존재 여부로 판단하고, 승인 대기는 진행 기록 존재 여부로 판단했습니다.
- 전달 대기와 담당 상담사는 내보내기 기록과 내보내기 시점의 담당 정보로 관리했습니다.

### 고객 정보 보호

- 어드민 목록은 상호명만 상시 노출하고 나머지 고객 정보는 별도 조회 경로로 열었습니다.
- 상담사 앱도 고객 칸을 목록에서 제외하고 필요한 식별자와 업무 상태만 읽도록 했습니다.
- 엑셀 내보내기는 기록을 남긴 뒤 파일을 만들었으며 다운로드한 파일의 통제 밖 유출은 별도 운영 절차가 필요합니다.
- 신청서와 열람 기록의 구체적인 민감 필드와 보관 수명은 `(보안)`으로 표시했습니다.

### 절차만 따라가는 체험 흐름

- 실제 접수·문자·실적과 분리된 체험 세션을 만들었습니다.
- 체험 세션은 다른 열린 QR을 닫지 않고 제출 시 신청서를 만들지 않으며 세션만 정리했습니다.
- 오래된 체험 세션은 정기 작업으로 삭제했습니다.

### 배운 점

- 통신 세션의 본인 확인과 만료를 재사용하면 개발 범위는 줄지만 대출인지 구분하는 값이 누락되면 실제 접수로 흘러갈 수 있습니다.
- 상태 칸을 새로 만드는 대신 이미 발생한 사건의 유무로 단계가 결정되도록 하면 불일치를 줄일 수 있습니다.
- 엑셀 내보내기와 진행 기록을 한쪽 창구만 수정하면 다른 창구로 단계를 건너뛸 수 있습니다.

## 14. 품질 게이트와 테스트

### 오늘 한 일

- TypeScript, Biome, Knip과 Vitest를 역할별 검사 도구로 나눴습니다.
- 실제 화면 오류는 jsdom 렌더 테스트로 재현했습니다.
- 데이터베이스 전이와 권한은 임시 Postgres 호환 환경에서 확인했습니다.

### 해결한 문제

- lint를 자동 수정하면 CI 위반이 성공으로 보일 수 있습니다.
- 계산 테스트만으로는 잘못된 이벤트 핸들러 연결을 잡을 수 없습니다.
- 미사용 코드는 import·변수·파일마다 다른 도구로 잡아야 합니다.

### 해결 방법

- 검사와 자동 수정 명령을 분리했습니다.
- 단위 테스트와 실제 컴포넌트 렌더 테스트를 나눴습니다.
- 마이그레이션과 권한 경계를 반복 가능한 테스트로 만들었습니다.
- 커버리지 임계값보다 위험이 큰 계산과 경계를 우선 테스트했습니다.

### 배운 점

- 개발 서버 통과와 운영 빌드 통과는 다른 검증입니다.
- 테스트 픽스처가 구현과 같은 잘못된 값을 복사하면 둘 다 틀려도 통과할 수 있습니다.
- 외부 문자 발송이나 실제 개인정보 열람은 테스트 환경에서 직접 실행하지 않고 별도 검증과 승인 절차가 필요합니다.

## 15. CI와 배포

### 오늘 한 일

- 앱별로 변경 경로를 좁혀 필요한 워크플로만 실행했습니다.
- 미리보기와 운영 배포를 분리했습니다.
- 데이터베이스와 앱의 배포 순서를 PR 본문과 마이그레이션 기록에 남겼습니다.

### 해결한 문제

- 배포가 성공해도 미리보기 또는 운영 별칭이 새 빌드를 가리키지 않을 수 있습니다.
- 경로 필터와 필수 체크 정책이 맞지 않으면 워크플로가 실행되지 않아도 머지 차단이 꼬일 수 있습니다.
- 구버전 앱이 남아 있는 상태에서 데이터베이스를 먼저 바꾸면 이전 기능의 의미가 달라질 수 있습니다.

### 해결 방법

- 배포 주소와 별칭을 명시적으로 확인했습니다.
- DB를 먼저 바꾸고 구버전 호환을 유지한 뒤 다음 릴리스에서 낡은 컬럼과 함수를 정리했습니다.
- 서버 액션은 `next build`와 실행 확인까지 포함해 검증했습니다.

### 배운 점

- CI 성공은 배포 주소가 최신이라는 뜻이 아닙니다.
- 앱별 워크플로와 브랜치 보호 정책은 함께 설계해야 합니다.
- DB 변경은 애플리케이션 호환성을 포함한 릴리스 단위로 봐야 합니다.
