## 기록 원칙

- **검증 결과 남기기:** 테스트, 빌드, 수동 확인 중 실제로 실행한 방법만 기록합니다.
- **결정 이유 기록하기:** 선택한 방법뿐 아니라 고려한 대안과 선택 이유도 적습니다.
- **개인정보·비밀 값 제외하기:** 토큰, 비밀번호, 실제 사용자 정보, 비밀 환경 변수는 기록하지 않습니다.
- **후속 작업 분리하기:** 완료한 일과 아직 하지 않은 개선점을 구분합니다.

## 앱과 패키지의 역할

| 경로 | 역할 | 기술·배포 형태(회고 시점) |
|---|---|---|

| `apps/admin` | 운영자 상품·신청·회원·정산 관리 | Vite + React, 필요한 서버 기능은 별도 함수로 분리 |

저장소는 pnpm workspace와 Turborepo를 이용해 여러 앱·패키지를 함께 관리했습니다. 내부 패키지를 앱에서 재사용해 복사본이 서로 달라지는 위험을 줄였습니다. 반면 배포 플랫폼의 함수 단위 번들링과 워크스페이스 해석이 맞지 않는 구간은 무리하게 공유하지 않고 별도 경계로 두었습니다.

### 모노레포에서 얻은 것과 남은 비용

- DB 타입을 공용 패키지로 모아 앱마다 테이블 타입이 갈라지는 것을 줄였습니다(PR #237).
- 상담사 앱에서도 계약 금액 계산을 써야 해 어드민의 계산·폼 로직을 공용 패키지로 옮겼습니다(PR #699). 계산을 복사하면 한 앱만 수정되어 결과 금액이 달라질 수 있기 때문입니다.
- 새 앱(지점장·상담사)을 추가하면서 앱별 CI와 배포 흐름도 확장했습니다(PR #590, #592 등).
- 내부 패키지는 설정을 단순하게 유지하기 위해 TypeScript 원본을 직접 소비하는 방식을 사용했습니다. 다만 모든 실행 환경에서 똑같이 동작하는 것은 아니어서 서버리스 함수 경계에는 별도 규칙이 필요했습니다.
- 개발 명령은 타입 검사, lint, 테스트를 일관되게 실행하도록 정리했습니다. `biome.json` 같은 루트 설정도 빌드 캐시 키에 포함해 오래된 검사 결과가 재사용되지 않도록 했습니다.

## 품질 게이트와 테스트 체계

### 검사 도구의 역할을 분리하다

미사용 코드를 한 도구에 모두 맡기지 않고 검사 범위에 따라 나눴습니다.

| 검사 대상 | 도구·방식 |
|---|---|
| 미사용 import | Biome |
| 미사용 변수·매개변수 | TypeScript 컴파일러 설정 |
| 사용되지 않는 파일·export·의존성 | Knip |
| 동작 규칙 | Vitest 단위 테스트 |
| 클릭·컴포넌트 연결 | jsdom 기반 렌더 테스트 |
| 번역·문자 메시지 제약 | 별도 검사 스크립트 |

초기에는 lint 명령이 자동 수정까지 해 CI의 위반을 고친 뒤 성공으로 끝날 수 있었습니다. 검사와 수정을 각각 `lint`와 `lint:fix`로 나눠 CI가 위반을 실제로 실패 처리하게 했습니다(PR #320). 미사용 코드 검사는 결과를 방치하면 쌓인다는 점을 확인해 findings를 정리한 뒤 CI 게이트로 승격했습니다(PR #317).

### 테스트는 위험이 큰 계산과 경계부터

처음 테스트를 도입할 때 모든 화면을 한꺼번에 덮기보다, 서로 같은 결과를 내야 하는 계산과 데이터 경계를 우선했습니다.

- 파트너 등급과 상태 전이, 휴대폰 견적·할부 계산, 카드 할인, 리베이트 지급액 등 금액과 규칙을 단위 테스트로 고정했습니다.
- 화면에서 훅은 정상이어도 잘못된 이벤트 핸들러를 연결하면 실제 동작이 깨질 수 있었습니다. 실제 화면 장애를 재현한 뒤 jsdom 렌더 테스트를 추가했습니다(PR #327).
- 테스트는 대상을 찾기 쉬운 위치에 두고, TypeScript 검사 범위에도 포함했습니다.
- 입력·번역·저장 규칙은 화면과 서버가 같은 검증 로직을 쓰게 하거나, DB 제약까지 포함해 검증했습니다.
- 마이그레이션의 주요 전이와 권한 경계는 임시 Postgres 호환 환경 등을 활용해 확인했습니다. 실제 외부 문자 발송은 비용과 부작용 때문에 자동 테스트에서 보내지 않고 별도 검증으로 분리했습니다.
- 테스트가 구현과 같은 값을 복사하면 둘 다 틀려도 통과할 수 있습니다. 번역 원문·화면 표기처럼 서로 다른 값이어야 하는 항목은 의도적으로 다른 픽스처를 사용했습니다.

커버리지 숫자는 어떤 파일을 분모에 포함하느냐에 따라 크게 달라질 수 있어, 같은 명령을 실행하면 같은 기준이 적용되도록 설정과 기준값 기록을 마련했습니다. 숫자 자체를 목표로 강제하는 임계값은 두지 않고, 중요한 동작과 회귀 위험을 테스트로 고정하는 쪽을 택했습니다.

### CI와 배포에서 배운 점

- 앱별로 변경 경로를 좁혀 불필요한 CI 실행과 배포를 줄이고, 연속 푸시에서는 오래된 작업을 취소하도록 했습니다.
- 경로 필터는 비용을 아끼지만 해당 워크플로가 실행되지 않은 상태가 필수 체크와 충돌할 수 있습니다. 브랜치 보호 정책을 적용할 때는 이 점을 함께 설계해야 합니다.
- 미리보기 배포와 운영 배포를 나누고, 배포 주소 별칭이 실제 새 빌드를 가리키는지 확인하는 단계를 명시했습니다.
- 배포 완료 표시만으로 고정 QA 주소가 새 버전을 가리킨다고 가정하면 안 된다는 사례를 겪었습니다(PR #266).
- DB 변경과 앱 배포는 호환성 순서가 설계의 일부입니다. 보통은 DB 변경을 먼저 적용한 뒤 소비 앱을 배포하고, 구버전이 아직 동작해야 하면 이전 함수·컬럼을 한 릴리스 뒤에 정리하는 확장-이전-축소 방식을 사용했습니다.
- CI 성공은 배포 안전을 보장하지 않습니다. 빌드 단계가 CI에 포함되지 않거나 운영 환경 설정이 다른 경우가 있어 별도 확인이 필요합니다.

## 디자인 시스템과 다국어

### 디자인 시스템

공용 디자인 시스템은 색·간격·타이포그래피 토큰, 재사용 UI 컴포넌트, 아이콘과 폰트를 제공했습니다. Figma 변경을 설명 문구만 보고 반영하면 세부 차이를 놓칠 수 있어 컴포넌트 노드와 토큰을 확인하고, 쇼케이스 렌더 결과를 디자인 기준과 비교하는 절차를 정리했습니다.

- 변형을 무조건 많은 prop으로 만들기보다 슬롯 조합이나 기존 상태에서 파생할 수 있는지 검토했습니다.
- 아이콘·브랜드 로고는 원본 에셋과 생성기를 단일 출처로 삼았습니다.
- 여러 앱의 CSS 유틸리티 충돌, 로케일별 폰트·자간, 공통 줄바꿈 규칙을 정리해 화면별 임시 보정을 줄였습니다.
- 공용 컴포넌트의 변경은 사용하는 앱들을 함께 확인해야 합니다. 토큰이나 공용 클래스의 작은 변화도 광범위하게 영향을 줄 수 있습니다.

### 8개 언어 지원

web은 한국어를 기준으로 영어·중국어·베트남어·러시아어·일본어·벵골어·몽골어를 포함한 8개 언어를 지원하도록 확장했습니다(PR #267~#298 등).

- 서버와 클라이언트가 현재 언어를 일관되게 알도록 로케일 상태를 관리하고, 번역 키 누락은 타입 검사로, 번역 값에 남은 원문 문자는 검사 스크립트로 찾았습니다.
- 서버 오류는 문장 대신 오류 코드를 전달하고 화면에서 번역하도록 변경했습니다. 사용자에게 직접 전달되는 문자 메시지는 서버가 번역하고 인코딩·길이 기준을 검사했습니다.
- DB 상품명은 코드 사전의 번역과 원문 fallback을 사용했습니다. 계약 기록에는 화면에 표시된 번역어가 아니라 접수 당시 원문을 저장해 기록의 의미가 사용자의 UI 언어에 따라 달라지지 않게 했습니다.
- 기관·은행·상품 이름 등 번역 여부가 모호한 항목은 화면에서 읽을 수 있어야 하는지와 운영상 식별 가능성을 함께 고려했습니다.
- 쿠키 기반 언어 설정은 첫 화면 표시를 일관되게 하지만 루트 렌더링의 정적 최적화를 줄일 수 있습니다. 공개 문서처럼 언어별 URL이 적합한 페이지는 경로 기반 로케일과 정적 생성으로 개선할 여지가 남았습니다.
- 번역은 기술 검사를 통과해도 통신·금융·제도 용어의 의미가 정확하다는 보장은 없습니다. 전문 용어와 숫자·조건은 사람 검수가 필요합니다.

## 영업 흐름과 상품 도메인

### 휴대폰 목록·상세·견적

- 휴대폰 상품 목록(PLP)에서 카테고리·검색·정렬을 제공하고, 영업 시작 시 상담에 필요한 조건을 순서대로 받도록 했습니다. 선택한 조건은 URL에 담아 상세 페이지와 연결했습니다.
- 상품 상세(PDP)는 통신사·요금제·복지 할인·보험·제휴카드 등 서로 다른 선택 축을 데이터 모델에 반영했습니다. 상품이 실제로 판매되는 통신사와 고객이 현재 이용하는 통신사는 다른 의미이므로 구분했습니다.
- 공통지원금은 기종·요금제·가입 유형에 따른 값으로 세분화했고, 비어 있는 값과 실제 0원을 구분하도록 고쳤습니다.
- 제휴카드 할인은 여러 장 선택, 카드별 할인 방식, 월 납부금 한도를 고려하도록 단계적으로 개선했습니다. 운영 데이터가 자유 텍스트인 경우를 해석하는 방식은 편리하지만 입력 문구 변경에 취약해, 장기적으로는 금액과 할인 유형을 구조화된 필드로 관리하는 것이 더 안전합니다.
- `buildQuote`를 단일 계산 출처로 두어 견적 카드와 최종 납부금이 서로 다른 계산을 하지 않게 했습니다. 공통지원금·선택약정의 택일, 할인 기준액, 음수 방지, 보험료 처리 등을 테스트로 고정했습니다.
- 이후 카드 할인과 결합 할인까지 견적에 포함했지만, 화면에서 계산된 계약 금액을 서버가 완전히 재계산하지 않는 구간은 신뢰 경계의 한계로 남았습니다.
- 통신사별 상품·보험·요금제 모델을 확장하고 정렬의 동률 기준을 명시해, 데이터베이스 반환 순서에 따라 상품 순서가 흔들리지 않도록 했습니다.

주요 변경 흐름: 휴대폰 목록·파트너 홈(#45~#46), 상세 데이터와 견적(#124, #131, #136, #188, #190), 카드·할인 및 신규 가입 흐름(#189, #212, #219, #486, #491, #529, #629), 상품별 판매 통신사(#540, #688).

### 인터넷 영업

인터넷은 휴대폰처럼 기종 안에 여러 통신사 옵션이 있는 모델이 아니라 통신사별 상품 자체를 선택하는 구조였습니다. 그래서 인터넷 상품·속도·TV 조합·부가서비스·결합 할인 등 별도의 데이터 모델을 구성했습니다.

- TV 결합 요금은 단순히 인터넷 요금과 TV 요금을 더하는 방식으로 실제 가격표를 표현할 수 없어 속도별 조합 가격을 저장했습니다.
- 파트너가 상담을 시작할 때 현재 사용 중인 인터넷을 확인하고, 선택한 통신사와 비교해 신규·이동·유지 상태를 파생했습니다.
- 한 통신사에 노출 상품이 여러 개 생겨 선택 경로가 모호해지지 않도록 운영 폼에서 노출 규칙을 확인하고, 상품 저장은 노출을 마지막에 켜도록 했습니다.
- 설치비·희망일·시간대 할증을 견적에 반영했습니다. 공휴일 목록은 코드 관리 비용과 매년 갱신 필요성이 남아 있어 운영 설정이나 갱신 검사를 고려할 수 있습니다.
- 결합 할인은 인터넷·휴대폰·유심의 계산 규칙을 구분하면서 공통 데이터 모델을 재사용했습니다. 속도 표기 차이로 요금이 적용되지 않았던 사례를 통해 저장과 조회가 같은 정규화 규칙을 사용해야 함을 확인했습니다.
- 상품 상세·최종 납부금·QR 흐름에서 같은 계산 결과를 사용하도록 하고, 계산에 영향을 주는 선택값은 확인 지문과 계약 스냅샷에도 반영했습니다.

주요 변경 흐름: 인터넷 스키마와 관리 화면(#349), 통신사별 상품과 진입 흐름(#362~#375), TV 조합·설치비·상세 견적(#510~#538), 결합 프로그램과 고객 대상 저장(#531~#595).

### 유심 영업

유심 영업은 별도 상품·신청 정보가 있지만 휴대폰 요금제와 고객 QR 입력 인프라를 재사용했습니다. 유심 요금제를 공용 요금제 모델에 합치고 상품군별 필터로 나눠 중복 데이터 모델을 줄였습니다.

- 선택약정, 유심 구매 여부, 배송 희망일, 제휴카드 등을 견적 규칙으로 구성했습니다.
- 이미 운영 중인 QR 세션·신청 흐름을 재사용하되, 상품군 간 데이터가 섞이지 않는지 읽기·쓰기 경계를 확인했습니다.
- 유심 탭은 인터넷 영업 페이지와 휴대폰 목록 양쪽에서 접근할 수 있도록 정리했습니다.
- 기능을 여러 차례 재구성하며 요금제의 초기·추천 노출 규칙을 단순화했습니다. 사용하지 않는 칼럼은 호환성 때문에 즉시 삭제하지 않고 후속 정리 대상으로 기록했습니다.

주요 변경 흐름: 유심 상품·접수(#392~#399), 요금제 통합(#408), 목록과 상세 개선(#447~#450, #501~#505), 진입 경로 통합(#507~#550), 납부 방식 공용화(#581~#584).

## QR 고객 입력과 신청 기록

### QR 세션과 고객 입력 흐름

파트너가 QR을 만들고 고객이 본인 휴대전화로 입력하는 흐름을 휴대폰·인터넷·유심에서 공유했습니��. QR은 단순한 화면 이동이 아니라 단계·만료·재진입·파트너와 고객의 권한을 함께 관리하는 세션 흐름으로 발전했습니다.

- 첫 구현은 브라우저 상태만으로 동작했지만, 새로고침·다른 기기·동시 진입 문제를 해결하려 서버가 세션 상태를 관리하도록 바꿨습니다(PR #239, #245).
- QR 스캐너가 링크를 미리 여는 동작 때문에 단순 1회용 진입은 실제 고객을 막을 수 있었습니다. 재진입을 허용하면서도 같은 QR을 여러 사람이 공유하지 않게 제한하는 절충을 설계했습니다. 상세 토큰·유예·합류 판정은 **(보안)**.
- 파트너 화면에는 고객 입력값을 보여주지 않고 세션 진행 상태만 표시하도록 했습니다.
- 고객 입력은 약관·가입자 정보·결제·배송·연락처·확인 등 단계로 나누고, 서버는 최소 진행 상태를 확인했습니다. 외부 인증 연동은 실제 공급자 검증이 끝나기 전까지 완료된 것으로 취급하지 않았습니다.
- 초안과 브라우저 저장소에는 민감 데이터가 남을 수 있으므로 보관 범위를 최소화하고 완료 후 정리하도록 했습니다. 구체적인 개인정보 필드와 암호화·보관 절차는 **(보안)**.
- 고객이 최종 제출하면 파트너가 후속 버튼을 누르지 않아도 신청이 접수되도록 개선했습니다. 다만 파트너가 다시 QR을 발급하는 흐름과 이미 제출된 신청의 취소·보존 관계를 함께 설계해야 했습니다(PR #726, #737, #744).

관련 설계의 배경은 원 프로젝트의 ADR 0003(회고 자료 기준)입니다. QR 세션 식별자, 개인정보 처리, 데이터 보관 기간 및 실제 연동 정보는 공개 문서에서 생략했습니다 **(보안)**.

### 민감 제출 정보와 계약 스냅샷

- 초기 고객 입력 화면은 값을 서버에 저장하지 않았습니다. 상담 업무에서 제출된 신청 정보를 확인할 필요가 생겨 저장 흐름을 추가했습니다(PR #324).
- 민감 필드와 일반 계약 내용은 저장 목적과 접근 방식이 다르므로 분리했습니다. 민감 값의 암호화·복호화 키 위치, 권한 세부사항, 감사 로그 스키마 및 보관 기간은 **(보안)**.
- 관리자나 상담사가 민감 정보를 열어볼 때는 접근 기록과 권한 확인이 필요한 설계를 적용했습니다. 원문 개인 정보를 일반 로그나 목록 응답에 섞지 않도록 했습니다.
- 계약 내용은 신청 시점의 상품 이름과 금액을 스냅샷으로 저장해, 나중에 상품명이 바뀌어도 과거 신청의 의미가 바뀌지 않게 했습니다.
- 번역 UI를 사용하는 경우에도 저장 기록은 원문 상품명으로 유지했습니다.
- 접수번호는 데이터베이스에서 발급해 동시 요청에서도 중복을 막고, 완료 화면과 재접속 화면의 동작을 구분했습니다(PR #336, #383~#389).
- 보관과 파기는 생성·수정뿐 아니라 재발급, 미완료 세션, 계정 탈퇴, 관리자 휴지통까지 연결됩니다. “삭제”가 어떤 데이터에 어떤 의미인지 경로별로 명시하고 테스트하는 것이 중요했습니다.

## 고객센터·프로필·파트너 센터

- 프로필에서는 이름·전화번호·추천 코드·수신 설정·로그인 수단·탈퇴 기능을 제공하고, 바뀐 값이 있을 때만 저장하도록 했습니다(PR #151).
- 배송 주소는 외부 주소 검색 도구를 지연 로드해 사용했고, 프로필과 고객 입력이 공통 로직을 재사용하도록 훅을 정리했습니다(PR #173).
- 고객센터는 FAQ, 문의 목록·작성·상세를 단계별로 구현한 뒤 실제 데이터 저장과 본인 문의만 조회하는 경계를 추가했습니다(PR #211~#248).
- 목록 필터·페이지·상태 처리의 중복을 공통 훅으로 정리했습니다. 현재 페이지보다 전체 페이지 수가 줄었을 때 빈 테이블이 되는 문제도 재현해 방지했습니다(PR #307~#308).
- 문의 상세는 존재 여부가 불필요하게 드러나지 않도록 처리하고, 시각 표시는 서비스 시간대 기준으로 통일했습니다.
- 파트너 센터의 GNB·LNB는 부업 목록의 단일 출처를 공유하도록 했습니다. 셸 상태와 URL 경계를 정리해 탭 이동 시 헤더 인디케이터가 초기화되는 문제를 줄였습니다.

## 운영자·지점장·상담사 업무 화면

### 권한별 업무 경계

운영 화면은 전체 운영자, 소속 범위가 있는 지점장·팀장, 담당 접수만 처리하는 상담사로 나눴습니다. 각각의 권한은 화면에서 메뉴를 숨기는 것만으로 구현하지 않고 서버에서 사용자·소속·담당 범위를 다시 확인하도록 했습니다. 정확한 데이터 뷰·함수 이름, 개인정보 열람 경로와 권한 부여 방식은 **(보안)**.

- 운영자는 전체 업무를 다루되 민감 데이터와 일반 목록을 분리했습니다.
- 지점장·팀장은 소속과 직급에 따라 볼 수 있는 파트너와 신청 범위를 계산합니다. 총괄매니저는 소속 선택을 필터로 쓰되, 권한 자체와 사용자의 선호 설정을 구분했습니다.
- 상담사 계정은 일반 회원과 분리하고, 담당 파트너 또는 건별 배정을 기준으로 접수 범위를 정했습니다.
- 권한 밖의 접수는 상세 내용을 읽은 뒤 버리는 것이 아니라, 상세 조회 전에 범위에서 제외하도록 했습니다.
- 화면을 나눈 결과 인증·세션·비밀번호 검증 등 일부 로직이 중복될 수 있었습니다. 민감한 공통 규칙은 같은 기대값의 테스트를 유지하고, 계산처럼 큰 도메인 로직은 공용 패키지로 분리했습니다.

### 통신 접수 관리와 업무 단계

- 휴대폰·유심·인터넷별 목록을 하나의 통신 접수 화면으로 통합했습니다(PR #596~#599).
- 한 상품군의 데이터 조회가 실패해도 나머지 상품군 업무가 함께 멈추지 않도록 부분 실패를 표현하고, 빠진 데이터가 없는 것처럼 오해되지 않게 알림을 추가했습니다.
- 접수의 흐름은 확약·진행·실적 확정 등 실제 업무 상태에 맞춰 확장했습니다. 상태가 늘어날 때 목록, 월별 집계, 파트너 실적, 정산·탈퇴 가드가 모두 같은 의미를 사용하는지 점검했습니다.
- 어드민 휴지통은 행을 무조건 삭제하는 대신 복구 가능한 표시 상태로 관리했습니다. 휴지통에 있는 신청을 파트너의 활동·등급·미지급 집계에서 어떻게 취급할지 한 곳에서 정의했습니다.
- 계약을 수정하는 경우 DB 함수에서 입력 검증과 변경 이력을 남기고, 민감 값의 수정은 일반 계약 변경과 분리했습니다(PR #650~#719).
- 이미 접수된 고객에 다른 상품을 추가하는 기능은 기존 고객 정보를 재사용하되, 추가 접수만 다른 고객으로 바뀌는 경우 원본 신청과 가족 연결 정보가 함께 오염되지 않도록 별도 경계를 마련했습니다(PR #674~#679).

### 정산과 등급

- 파트너 등급은 월별 실적의 상태 기계로 바꾸고, 현재 등급과 월별 타임라인이 같은 계산을 공유하도록 했습니다(PR #305, #418, #442~#444).
- 등급 산정과 정산 대상은 서로 다른 사건·상태 축으로 관리했습니다. 과거 실적을 나중에 철회해도 당시 승급 판정이 소급 변경되지 않도록 기록 시점을 구분했습니다.
- 정산은 계좌 등록, 지급 신청, 운영자 지급 완료, 지급 취소·보관을 단계적으로 연결했습니다(PR #172, #422~#433).
- 예상 수익은 운영 정책 값을 브라우저에 내려 계산하지 않고 서버에서 필요한 결과만 반환하도록 개선했습니다(PR #482, #630, #633).
- 상태를 추가할 때 화면 한 곳만 바꾸면 월별 수익 또는 탈퇴 가능 여부가 어긋날 수 있었습니다. 새 상태를 도입할 때는 “미지급 금액”과 “확정 실적”처럼 집계의 목적을 나눠 사용처 전체를 점검해야 한다는 점을 배웠습니다.
- 지급·계좌·세금·개인별 금액 등 구체적인 재무 정보는 이 회고에 포함하지 않습니다 **(보안)**.

### 상담사 앱

상담사 앱은 담당 접수 조회, 문의 답변, 진행 단계, 계약 수정, 고객 정보 열람과 상담 메모를 지원했습니다(PR #686~#724 등).

- 상담사 전용 데이터 범위를 뷰와 서버 함수에서 함께 확인했습니다.
- 기존 어드민 업무 규칙을 재사용하되 “누가 작업했는가”를 변경 이력과 감사 기록에 구분해 남기도록 확장했습니다.
- 개발 서버에서는 통과했지만 프로덕션 빌드에서 서버 액션의 타입 재내보내기 때문에 실패한 사례가 있었습니다(PR #710). `next dev`만으로 확인하지 않고 프로덕션 빌드와 실행 환경까지 확인해야 한다는 교훈을 얻었습니다.
- 업무 메모를 어드민과 상담사 사이에서 공유했다가 작성자·가시성 의미가 달라 별도 모델로 분리했습니다.

## 대출(정책자금) 영업

2026년 10월에는 통신 외 첫 영업 도메인으로 대출 접수 흐름을 추가했습니다(PR #727~#777).

- 고객은 모바일에서 사업장·재무·연락처 정보를 입력하고 제출합니다. 대출 신청은 기존 QR 흐름의 세션·단계 관리 원칙을 재사용했습니다.
- 절차 체험용 흐름은 실제 접수·문자·실적과 분리하고, 기존 고객 세션에 영향을 주지 않도록 했습니다.
- 접수 단계는 “접수 대기 → 전달 대기 → 승인 대기 → 실적 확정”으로 정리했습니다. 별도 상태를 무조건 추가하기보다 내보내기 기록·진행 기록·실적 기록처럼 이미 발생한 사건에서 단계를 파생하는 방식을 사용했습니다.
- 고객 정보는 업무상 필요한 구간에서만 조회하거나 내보내도록 단계적으로 수정했습니다. 대출 신청의 구체적인 민감 필드, 엑셀 열 구성, 저장·열람 경로는 **(보안)**.
- 내보내기 이력은 남길 수 있지만 다운로드한 파일은 시스템 통제 밖으로 나갈 수 있습니다. 다운로드 권한과 파일 취급은 별도의 운영 절차가 필요합니다.
- 통신 접수와 비슷한 업무 배치를 재사용하면서도 대출은 확약 없이 외부 전달로 시작한다는 차이를 반영했습니다.

## 아직 개선 여지가 있는 부분

회고 자료에서 확인된 후속 과제입니다. 현재 해결됐다고 단정하지 않으며, 원 프로젝트의 후속 진행 여부는 별도 확인이 필요합니다.

- 공개 페이지 일부에서 쿠키 기반 언어 선택이 정적 렌더링을 제한했습니다. URL 로케일과 정적 생성·ISR을 검토할 수 있습니다.
- 상품 번역 사전은 원문 이름이 바뀌거나 특정 환경에만 있는 상품을 조용히 놓칠 수 있습니다. DB 값과 번역 키를 비교하는 자동 점검, 관리 화면 기반 번역을 검토할 수 있습니다.
- 요금제·카드 혜택의 자유 텍스트를 코드에서 해석하는 부분은 데이터 입력 변경에 취약합니다. 금액·유형을 구조화된 필드로 관리하는 것이 개선 방향입니다.
- 휴대폰·인터넷·유심 견적 계산은 클라이언트와 운영자 편집 경로 사이에 계산 로직이 남을 수 있습니다. 계약 확정이 필요한 구간에서 서버가 같은 규칙으로 재계산·대조하는 방안을 검토할 수 있습니다.
- 화면과 서버에서 복제된 보안·비밀번호 관련 구현은 변경 시 함께 갱신해야 합니다. 민감한 코드는 공유 경계와 배포 환경을 검증한 뒤 공용화하는 것이 바람직합니다 **(보안)**.
- 일부 공휴일·외부 인증 연동은 수동 유지 또는 실제 연동 전 단계가 남아 있었습니다. 운영 소유자, 갱신 주기, 완료 기준을 명시해야 합니다.
- jsdom은 실제 브라우저 레이아웃·외부 연동·전체 여정을 검증하지 못합니다. 중요한 고객 흐름에 한해 브라우저 기반 종단 테스트를 추가할 수 있습니다.
- DB 마이그레이션의 회귀 테스트와 권한 검증을 팀이 반복 실행할 수 있도록 공통 테스트 하네스로 정리할 여지가 있습니다.
- CI의 경로 필터와 필수 체크 정책은 함께 설계해야 합니다. 스킵된 워크플로와 머지 차단 조건을 정기적으로 확인해야 합니다.
- 개인정보 보관·파기 정책은 실제 법률·업무 목적에 맞춰 담당자가 검토해야 합니다. 이 문서는 법률 자문이나 최신 운영 정책을 대신하지 않습니다 **(보안)**.

## 회고를 관통하는 원칙

> **같은 계산과 규칙은 공유하고, 다른 역할과 데이터는 경계로 나눈다. 문제가 생기면 재현 가능한 테스트와 기록으로 다음 회귀를 막는다.**

- 공유: 디자인 토큰, 데이터베이스 타입, 견적 계산, 목록 처리, 번역 검증 규칙.
- 분리: 앱별 사용자 역할, 고객 입력과 파트너 화면, 민감정보와 일반 계약 스냅샷, 미리보기와 운영 배포.
- 기록: 마이그레이션, ADR, 변경 이력, 테스트 결과와 남은 한계.
- 절제: 검증할 수 없는 최신 상태를 단정하지 않고, 민감한 운영 세부 사항은 공개 문서에서 다루지 않는다.
