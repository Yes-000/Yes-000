# 2026-11-21 — 웹 제작 프로세스와 PR 협업 학습

> 이 기록은 신규 웹 프로젝트를 준비하고, 품질을 확인하며, PR과 배포를 안전하게 진행하기 위해 학습한 절차와 설계 원칙을 정리합니다. 명령과 설정은 프로젝트별로 달라질 수 있으므로 실제 저장소의 문서와 스크립트를 우선 확인합니다.

## 신규 웹 프로젝트 준비

### 사전 준비

- Node.js와 pnpm을 설치합니다.
- GitHub 저장소 생성 권한과 배포 환경(Vercel 등)을 확인합니다.
- 필요한 환경 변수의 이름과 발급처를 파악하되, 실제 비밀 값을 코드나 문서에 기록하지 않습니다.

### 프로젝트 생성과 기본 품질 확인

- Next.js 프로젝트를 생성하고 프로젝트 규칙과 사용 명령을 문서화합니다.
- `package.json`의 스크립트로 타입 검사, 린트, 전체 품질 검사를 실행할 수 있도록 구성합니다.
- `pnpm check-all`처럼 한 명령으로 검사를 실행하는 흐름을 익혔습니다. 실제 스크립트 명령은 프로젝트 설정을 따라야 합니다.
- CI에서는 파일을 자동 수정하는 lint 명령보다 검사 전용 명령을 실행해, 로컬 코드와 CI 검증 대상이 달라지지 않도록 합니다.

```json
{
  "scripts": {
    "type-check": "tsc --noEmit",
    "lint": "biome check ./src ./next.config.ts",
    "check-all": "pnpm run type-check && pnpm run lint"
  }
}
```

환경 변수 타입 선언은 프로젝트가 실제 사용하는 변수에 맞춰 관리합니다. 타입 선언은 오타를 줄이는 데 도움이 되지만, 런타임에 값이 설정되어 있음을 보장하지는 않으므로 실행 시 누락 여부도 확인해야 합니다.

### 서비스 연동과 유틸리티

- Supabase 프로젝트를 만들고 `.env.local` 등 로컬 전용 설정에 연결 정보를 둡니다.
- `clsx`와 `tailwind-merge`를 조합한 `cn` 유틸리티가 조건부 클래스와 Tailwind 클래스 충돌을 정리하는 데 쓰일 수 있음을 익혔습니다.
- 배포 플랫폼에도 환경별 변수를 설정하고, 외부 API 키 발급처에서 도메인 허용 설정이 필요한지 확인합니다.
- 키는 공개 설정과 서버 비밀 값으로 구분하고, 서버 전용 키를 `NEXT_PUBLIC_*` 변수나 브라우저 코드에서 사용하지 않습니다.

### Supabase CLI와 로컬 개발

- `supabase projects list`로 접근 가능한 프로젝트와 project ref를 확인합니다.
- `supabase link` 또는 `supabase link --project-ref <ref>`로 현재 저장소를 명시한 프로젝트에 연결합니다.
- `supabase start`, `supabase status`, `supabase stop`으로 로컬 Supabase 스택을 시작하고 상태를 확인한 뒤 종료하는 흐름을 익혔습니다.
- 로컬 웹 앱과 로컬 Supabase를 함께 쓸 때 URL과 키가 같은 환경을 가리키는지 확인합니다. 개발·운영 프로젝트와 키를 혼동하지 않도록 환경을 분리합니다.

## PR 협업과 리뷰

### 제목과 설명

- PR 제목은 변경 의도가 드러나도록 작성합니다. 예: `feat(search): 필터 UI와 API 쿼리 연결`.
- 본문에는 왜 변경하는지, 무엇을 바꿨는지, 어떻게 검증했는지 기록합니다. UI 변경이면 전후 스크린샷이나 녹화, 관련 이슈·Figma·PR을 함께 연결할 수 있습니다.
- 리뷰어가 집중할 파일이나 로직, 영향 범위와 부작용, 테스트 방법을 명확히 적습니다.
- 민감한 환경 변수와 키를 PR에 포함하지 않습니다. 필요한 경우 실제 값 없는 `.env.example`을 제공합니다.

### PR 크기와 커뮤니케이션

- 리뷰 가능한 작은 단위로 PR을 유지하고, 포맷 변경·리팩터링·기능 변경은 가능하면 구분합니다.
- 커밋도 의미 단위로 나눠 변경 의도를 추적하기 쉽게 합니다.
- PR을 열기 전에 base 브랜치를 최신화하고 충돌 가능성을 확인합니다. rebase, squash 등 히스토리 정리 방식은 팀 규칙을 따릅니다.
- 리뷰 의견을 반영하지 않을 때는 이유와 대안을 설명하고, 합의된 결론은 PR에 남깁니다.
- 머지 전에 디버그 코드, 실험 플래그, 성능·번들 영향과 필요한 배포 절차를 확인합니다.

### 올리기 전 품질 확인

- 프로젝트에서 정한 전체 검사(예: `pnpm check-all`)를 실행하고 결과를 기록합니다.
- 불필요한 `any` 사용을 피하고, 오류·실패 UI, 타임아웃과 재시도 등 예외 상황을 고려합니다.
- 인증·인가는 UI에서 숨기는 것으로 끝내지 않고 서버에서 최종 권한을 확인합니다.
- 외부 서비스 연동과 실제 고객 데이터 접근은 안전한 테스트 환경과 승인 절차를 사용합니다.

## DB 변경과 배포 안전성

애플리케이션 코드와 데이터베이스 스키마는 배포 시점이 달라 구버전과 신버전이 잠시 공존할 수 있습니다. 칼럼을 즉시 삭제하거나 이름을 바꾸기보다 **Expand → Migrate → Contract** 순서로 호환성을 유지하는 방법을 배웠습니다.

1. **Expand:** 기존 구조를 유지하면서 새 칼럼이나 테이블을 호환 가능한 형태로 추가합니다.
2. **Migrate:** 데이터를 백필하고, 새 코드가 구·신 구조를 안전하게 읽고 쓸 수 있도록 전환합니다.
3. **Contract:** 구버전 앱이 더는 옛 구조를 사용하지 않는 것이 확인된 뒤 별도 변경으로 정리합니다.

마이그레이션은 파일로 버전 관리하고 적용 대상, 실행 결과와 순서를 확인합니다. 배포 전에는 마이그레이션이 새 코드보다 먼저 반영되는지, 구버전도 동작하는지, 민감 데이터가 목록 API·로그에 섞이지 않는지, 승인과 롤백 절차가 있는지 확인합니다.

## Next.js App Router와 레이아웃

- GNB/LNB 같은 공통 UI 셸은 `layout.tsx`에 두고, 페이지나 View는 주요 콘텐츠를 담당하도록 책임을 나누는 원칙을 익혔습니다.
- 공통 레이아웃에서 라우팅 정보를 이용해 현재 메뉴를 표시하면 각 페이지에서 네비게이션 UI를 중복 구현하지 않아도 됩니다.
- 고정 영역과 늘어나는 콘텐츠 영역을 구분합니다. 세로 구성에서는 헤더를 고정하고 main에 남은 높이를 할당하며, 가로 구성에서는 LNB를 고정 폭으로 두고 콘텐츠가 나머지 너비를 차지하도록 할 수 있습니다.
- flex 내부 스크롤과 긴 콘텐츠의 overflow 문제를 줄이기 위해 `min-height: 0`, `min-width: 0`, 적절한 `overflow`를 함께 고려합니다. 스크롤을 어느 영역에 둘지도 명시합니다.

```css
.app {
  height: 100vh;
  display: flex;
  flex-direction: column;
}

.header {
  flex: 0 0 auto;
}

.body {
  flex: 1;
  display: flex;
  min-height: 0;
}

.lnb {
  width: 240px;
  flex: 0 0 auto;
}

.content {
  flex: 1;
  min-width: 0;
  overflow: auto;
}
```

## Next.js 이미지와 성능

- Next.js에서 일반 `<img>` 사용 시 최적화 관련 경고가 발생할 수 있으며, 적절한 경우 `next/image`의 `<Image />`를 고려합니다.
- 이미지 크기를 알 수 있으면 `width`와 `height`를 지정하고, 부모 크기에 맞추는 `fill` 사용 시 부모의 위치와 크기를 설정합니다.
- 반응형 이미지에는 `sizes`를 검토하고, 외부 이미지 URL은 `next.config`의 허용 설정을 확인합니다.
- 경고가 난 파일과 줄을 확인하거나 코드 검색으로 사용 위치를 찾은 뒤, 모든 `<img>`를 무조건 바꾸기보다 사용 맥락과 프로젝트 설정에 맞춰 처리합니다.

## 배운 점

- 프로젝트 시작 단계에서 실행 가능한 품질 검사와 환경 설정 기준을 마련하면 이후 작업을 반복 가능하게 만들 수 있습니다.
- PR은 코드 전달뿐 아니라 변경 배경, 검증 방법, 리뷰가 필요한 지점을 공유하는 문서입니다.
- DB와 애플리케이션은 동시에 교체되지 않을 수 있으므로 배포 중 호환성을 설계해야 합니다.
- 레이아웃은 화면 구성과 스크롤 책임을, 페이지 컴포넌트는 실제 콘텐츠를 담당하도록 분리하면 변경 범위를 줄일 수 있습니다.
- 이미지는 최적화 이점과 외부 리소스 설정을 함께 고려하고, 도구의 경고를 프로젝트 맥락에서 확인합니다.
