# 2026-11-21 — 컴포넌트 구조·Git·라우팅 학습

> 이 기록은 React 컴포넌트 분리와 디렉터리 규칙, Git 작업, Next.js 라우터 동작, 리팩터링과 프로젝트 템플릿에 대해 학습한 내용을 정리합니다. 명령과 구조는 프로젝트 및 팀 규칙을 우선합니다.

## 컴포넌트 크기와 역할 분리

- React 컴포넌트 파일은 일정 크기를 넘으면 데이터 조회, 상태·이벤트 처리, UI 블록, 정적 데이터를 각각 책임에 맞게 분리하는 방법을 익혔습니다.
- 300줄 이하를 팀의 참고 기준으로 삼을 수 있지만, 줄 수 자체가 절대적인 품질 기준은 아닙니다. 독립적인 역할과 변경 이유가 있는지를 보고 분리 여부를 판단합니다.
- JSX 블록이 독립된 UI 역할을 가지면 하위 컴포넌트로, 상태·effect·핸들러가 하나의 도메인으로 묶이면 커스텀 훅으로, 정적 옵션이나 상수는 별도 모듈로 추출할 수 있습니다.
- 뷰에서만 쓰는 요소는 해당 `views/` 아래에 가까이 두고, 여러 화면에서 재사용할 때 `src/components`나 `src/hooks`로 올리는 방식이 응집도를 높입니다.

## 디렉터리 구조와 Export 규칙

- 라우팅과 UI 로직을 분리합니다. `app/`은 URL 연결과 프레임워크 파일을 담당하고, 화면과 그 로직은 `views/`에 둘 수 있습니다.
- 예를 들어 `src/app/search/page.tsx`는 SearchView를 렌더링하고, 검색 상태와 UI는 `src/views/SearchView/`에 둡니다.
- View 전용 컴포넌트와 훅은 View 폴더에, 여러 View에서 쓰는 컴포넌트와 훅은 공용 디렉터리에 둡니다. 전역 상태는 Provider와 훅을 함께 제공할 수 있습니다.
- Next.js가 특별히 요구하는 라우트 파일은 프레임워크 규칙에 따르고, 그 외 컴포넌트와 훅의 named/default export 기준은 팀 컨벤션으로 통일합니다.

## Git 브랜치와 커밋 학습

### 스택형 PR

- 후속 브랜치의 base가 앞선 기능 브랜치인 PR 체인을 스택으로 관리하는 방식을 익혔습니다.
- 각 PR은 가능한 한 독립적으로 리뷰 가능한 단위가 되도록 나누고, 아래 단계부터 검토하면 기반 변경을 먼저 확인할 수 있습니다.
- 하위 PR이 병합되거나 rebase되면 후속 PR의 base와 diff를 다시 점검합니다. 스택이 지나치게 길어지지 않도록 중간 단계를 정리합니다.

### 브랜치 이름 변경

- 로컬 브랜치 이름을 변경한 뒤 새 원격 브랜치를 올리고, 기존 원격 브랜치가 더 이상 필요 없는지 확인한 후 삭제하는 절차를 익혔습니다.

```bash
git branch -m <new-branch-name>
git push -u origin <new-branch-name>
git push origin --delete <old-branch-name>
```

공유 브랜치 이름을 바꾸기 전에는 협업자와 연결된 PR 및 자동화 영향을 확인합니다.

### 커밋 참조와 수정 위치 기록

- 커밋 해시나 링크를 PR 설명에 남기고, 변경 파일·기능·이유·검증 방법을 함께 설명하면 리뷰 맥락을 찾기 쉽습니다.
- 라인별 설명이 필요하면 GitHub의 변경 파일 화면에서 코드 라인에 코멘트를 남길 수 있습니다.

### Reset을 이용한 로컬 커밋 정리

- `git reset --soft HEAD~N`은 지정한 커밋을 되돌리되 변경 내용을 staged 상태로 남깁니다.
- `git reset --mixed HEAD~N`은 커밋을 되돌리고 변경 내용을 unstaged 상태로 남깁니다. `--mixed`는 기본값입니다.
- `git status`로 현재 staged/unstaged 변경을 확인합니다.
- 이미 원격에 공유한 커밋을 reset으로 재작성하면 협업자에게 영향을 줄 수 있으므로, 공유 여부와 팀 절차를 먼저 확인합니다. 삭제된 작업을 복구하기 어려울 수 있으니 reset 전 현재 상태를 점검합니다.

## Next.js Router 히스토리 동작

- `back()`은 브라우저의 이전 히스토리 항목으로 돌아갑니다.
- `push('/path')`는 새 히스토리 항목을 추가해 이동하므로 뒤로 가기로 이전 화면에 돌아갈 수 있습니다.
- `replace('/path')`는 현재 항목을 대체합니다. 완료 페이지나 중복 제출을 막아야 하는 흐름에서는 사용 목적과 뒤로 가기 동작을 고려해 선택합니다.

## 리팩터링과 변경 단위

- 폰트 삭제처럼 파일 정리, 컴포넌트 이동·이름 변경, 경로 변경은 영향 범위를 확인하고 의미 있는 단위로 나누는 방법을 익혔습니다.
- 파일 이동과 로직 변경을 분리하면 diff에서 이동 자체와 동작 변경을 구분하기 쉬울 수 있습니다.
- 컴포넌트가 한 화면에서만 쓰이는지 확인한 뒤 가장 가까운 소유 디렉터리로 이동하고, View·라우트·페이지 이름을 일관되게 맞춥니다.
- 리팩터링 후 import 경로, 라우트, 빌드와 테스트를 확인합니다.

## 프로젝트 템플릿

- Next.js App Router와 React/Vite 프로젝트의 템플릿을 각각 준비해 시작 시 참고할 수 있음을 익혔습니다.
- 템플릿을 복사할 때는 폴더 구조, 스크립트, 품질 검사 규칙과 프로젝트 요구사항을 확인하고 불필요한 규칙을 그대로 강제하지 않습니다.

## 보안과 계정 설정 관련 메모

- Git의 `user.email` 설정은 커밋 작성자 정보이며, 계정 접근 토큰이나 비밀 키와는 별개의 값입니다.
- 단축 명령(alias)은 개인 개발 환경 편의를 위한 설정이므로, 공유 작업에서는 실제 실행 명령을 팀 문서에 명확히 남깁니다.
- 외부 플랫폼의 토큰·사용량·결제 관련 제한은 해당 플랫폼의 공식 안내와 계정 설정을 확인합니다. 민감한 토큰은 저장소나 로그에 기록하지 않습니다.

## 배운 점

- 컴포넌트의 파일 크기보다 역할과 변경 이유를 기준으로 분리해야 과도한 추출과 거대한 파일을 모두 피할 수 있습니다.
- 디렉터리는 라우팅·화면·재사용 범위를 보여주는 구조이며, 팀에서 합의한 규칙을 일관되게 적용해야 합니다.
- 스택형 PR은 의존 관계를 드러내지만 각 PR의 범위와 base를 꾸준히 관리해야 합니다.
- `reset`은 staged 상태와 공유 커밋 여부에 영향을 주므로 실행 전 작업 트리와 브랜치 상태를 확인합니다.
- 라우터의 push/replace/back은 브라우저 히스토리 경험을 바꾸므로 화면 흐름에 맞춰 선택합니다.
