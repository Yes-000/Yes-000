# 여기쏘(Yeogisso) 아키텍처, 처음부터 쉽게 풀어보기

이 문서는 기술 노트(ARCHITECTURE.md)에 나온 각 결정을 **“이게 뭔지 → 왜 했는지 → 뭐가 좋은지 → 다른 방법은 뭔지 → 그런데 왜 굳이 이걸 골랐는지”** 순서로, 입문자 눈높이에서 풀어 쓴 해설서입니다. 면접에서 “왜 이렇게 했어요?”라고 물었을 때 설명할 수 있도록 비유와 비교표를 함께 넣었습니다.

## 먼저: 이 서비스가 뭐 하는 건지 한 줄로

여기쏘는 부업 파트너가 상품을 배우고, 영업하고, 정산받는 플랫폼입니다. 쓰는 사람이 세 종류예요.

| 사용자 | 하는 일 | 비유 |
| :--- | :--- | :--- |
| 방문자(소비자) | 상품 구경, 가입 | 백화점에 그냥 온 손님 |
| 부업 파트너 | 상품 학습·영업·정산 | 백화점에 입점한 판매원 |
| 운영자(어드민) | 상품·파트너 관리 | 백화점 관리사무소 직원 |

세 사람이 필요로 하는 화면과 보안 수준은 완전히 다릅니다. 이 “다름”을 어떻게 나누고 어떻게 공유했는가가 이 프로젝트 설계의 핵심 주제예요.

## 1. 왜 “모노레포 + 두 개의 프레임워크”인가

### 1-1. 모노레포가 뭐예요?

모노레포(monorepo)는 여러 앱·라이브러리를 하나의 Git 저장소(폴더) 안에서 관리하는 방식입니다. 반대는 멀티레포(폴리레포)로, 앱마다 저장소를 따로 두는 방식입니다.

여기쏘 저장소 (하나)

```text
├── apps/web       ← 소비자·파트너용 사이트
├── apps/admin     ← 운영자용 관리 화면
└── packages/
    ├── design-system     ← 공통 디자인 부품
    └── database-types    ← DB 스키마 타입
```

비유하자면, 집 한 채 안에 방(앱)이 여러 개 있고, 거실·주방(공통 부품)은 모두가 같이 쓰는 구조입니다. 방을 각각 다른 건물에 지으면(멀티레포) 주방을 쓰려고 매번 옆 건물까지 걸어가야 하죠.

#### 왜 좋은가

- 공통 부품(디자인, DB 타입)을 한 곳에 두고 모두가 즉시 씁니다. 복사·붙여넣기와 버전 어긋남이 줄어듭니다.
- 여러 앱을 한 번에 고치는 변경(예: 버튼 디자인 통일)을 하나의 PR로 처리할 수 있습니다.

#### 대안과 비교

| 방식 | 장점 | 단점 | 여기쏘 선택 이유 |
| :--- | :--- | :--- | :--- |
| 멀티레포(앱마다 저장소) | 앱별 독립성 최고, 권한 분리 쉬움 | 공통 코드 공유가 고통(npm 배포·버전 관리) | 혼자 또는 소규모 팀이라 공유 이득이 훨씬 큼 |
| 모노레포(선택) | 공통 코드 즉시 공유, 일괄 변경 쉬움 | 저장소가 커지고 빌드 관리 필요 | Turborepo로 빌드 관리 해결 |

### 1-2. pnpm + Turborepo는 왜?

**pnpm**은 패키지(라이브러리) 설치 도구입니다. npm·yarn의 형제인데, 같은 라이브러리를 앱마다 중복 저장하지 않고 한 번만 저장해서 연결합니다. 그래서 디스크 사용량과 설치 시간이 줄고, 모노레포의 워크스페이스(여러 앱 묶음)를 잘 지원합니다.

**Turborepo**는 모노레포 빌드 가속기입니다. “이미 빌드한 건 또 안 한다(캐시)”, “안 바뀐 앱은 건너뛴다”를 해줍니다.

비유하면 pnpm은 공용 창고(라이브러리를 한 번만 쌓아두고 방마다 연결), Turborepo는 작업 반장(안 바뀐 일은 다시 안 시킴)입니다.

대안으로 npm·yarn workspaces도 가능합니다. 다만 설치 효율(pnpm)과 캐시 빌드(Turborepo)를 함께 챙기면 큰 모노레포일수록 체감이 큽니다.

### 1-3. 진짜 핵심 결정 — 왜 web은 Next.js, admin은 Vite로 갈랐나

이 프로젝트에서 가장 설명할 가치가 큰 판단입니다. **“둘 다 리액트인데 왜 프레임워크를 다르게 썼냐”**는 질문이 나올 수 있어요.

먼저 두 앱의 요구가 다릅니다.

| 구분 | apps/web (소비자·파트너) | apps/admin (운영자) |
| :--- | :--- | :--- |
| 누가 봄 | 불특정 다수, 검색엔진도 봄 | 소수의 내부 직원만 |
| 중요한 것 | 첫 화면 빠르게 + SEO(검색 노출) | 로그인 뒤 기능 밀도 |
| 성격 | 공개 웹사이트 | 사내 도구(대시보드) |

**Next.js(web에 사용):** 서버에서 HTML을 미리 만들어 보내는(SSR/서버 컴포넌트) 기능이 강점입니다. 그래서 첫 화면이 빠르고, 구글 같은 검색엔진이 내용을 잘 읽어 SEO에 유리합니다. 공개 사이트에 잘 맞아요.

**Vite + React(admin에 사용):** 브라우저에서 JavaScript로 화면을 그리는 SPA(단일 페이지 앱)입니다. SEO가 필요 없는 로그인 뒤 내부 도구라면 서버 렌더링의 복잡함을 짊어질 이유가 없습니다. Vite는 개발 중 새로고침이 매우 빠른 것이 강점이라 내부 도구 개발 속도를 높여 줍니다.

한 줄 논리: “공개해서 검색에 걸려야 하는 곳(web)엔 서버 렌더링(Next), 로그인 뒤 우리끼리 쓰는 도구(admin)엔 가볍고 빠른 SPA(Vite).” 필요가 다르니 도구도 다르게 쓴 것이고, 디자인·DB 타입은 공유해서 중복을 줄였습니다.

#### 대안 비교

| 대안 | 왜 안 골랐나 |
| :--- | :--- |
| 둘 다 Next.js | admin에는 SSR·SEO가 필요 없는데 그 복잡도를 떠안게 됩니다. Vite의 빠른 개발 경험도 포기합니다. |
| 둘 다 Vite(SPA) | web의 SEO·첫 로딩 이점을 포기하게 됩니다. 공개 서비스에 불리할 수 있습니다. |
| web=Next / admin=Vite (선택) | 각 앱의 실제 요구에 최소 복잡도로 맞춥니다. 공통 코드는 패키지로 공유합니다. |

**면접 포인트:** “프레임워크를 통일하지 않은 건 유행이 아니라 각 앱의 요구(SEO 유무, 사용자 범위)에서 역산한 결정”이라고 설명하면 좋습니다.

### 1-4. 나머지 스택 한눈에

| 기술 | 쉬운 설명 | 왜 이걸? | 대안 |
| :--- | :--- | :--- | :--- |
| React 19 + App Router | 화면 만드는 기본 틀. 서버 컴포넌트로 서버에서 그림 | 첫 로딩·SEO 확보, 상호작용 부분만 브라우저로 | Pages Router, Remix 등 |
| Route Handler(BFF) | Next 안에 만든 미니 서버(API) | 별도 백엔드 서버 없이 서버 로직 처리 | 별도 Node/Nest 서버(운영 부담 증가) |
| Supabase | 관리형 Postgres DB + 인증 + 파일 | DB·인증·보안을 한 번에, 서버 운영 부담 감소 | 직접 세운 Postgres+백엔드(할 일 증가) |
| Vercel | 배포 플랫폼 | Next와 궁합이 좋고, 미리보기 배포가 자동 | AWS 직접 구성(복잡) |
| TypeScript + Biome | 타입 검사 + 린트/포맷 도구 | 실수를 컴파일 때 잡고, 코드 스타일 통일 | ESLint+Prettier(설정이 더 많을 수 있음) |

**BFF(Backend For Frontend)**는 “프론트를 위한 백엔드”라는 뜻입니다. Next.js의 `app/api/*` 폴더에 서버 코드를 두면 프론트엔드 프로젝트 안에 필요한 만큼의 서버가 같이 사는 셈입니다. 별도 서버를 세우고 운영·배포하는 부담을 줄일 수 있어 규모와 팀이 작을 때 특히 이득입니다.

## 2. 폴더 구조와 화면 나누기 — “왜 이렇게 잘게 쪼갰나”

### 2-1. Layout(껍데기) / View(내용) 분리

Next.js에서 `app/` 폴더는 URL 주소(라우팅)를 담당합니다. 여기쏘는 `app/`을 얇게 유지하고, 실제 화면 조립은 다른 곳에 둡니다.

```text
app/(sidejob)/layout.tsx  →  <SidejobShell>{children}</SidejobShell>   // 주소·틀만
shells/SidejobShell/      →  헤더(GNB) + 스크롤 영역                    // 공통 껍데기
app/support/page.tsx      →  <SupportView />                             // “이 주소는 이 화면” 연결만
views/SupportView/        →  실제 화면 조립                              // 진짜 내용
```

> 원문에서 공유된 내용은 여기까지입니다. 다음 절은 이어서 추가할 수 있도록 비워 두었습니다.
