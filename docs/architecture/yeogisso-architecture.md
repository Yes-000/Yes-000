> 이 문서는 여러분이 만든 기술 노트(ARCHITECTURE.md)에 나온 각 결정을
> **"이게 뭔지 → 왜 했는지 → 뭐가 좋은지 → 다른 방법은 뭔지 → 그런데 왜 굳이 이걸 골랐는지"**
> 순서로, 입문자 눈높이에서 하나씩 풀어 쓴 해설서입니다.

## 먼저: 이 서비스가 뭐 하는 건지 한 줄로

여기쏘는 **부업 파트너가 상품을 배우고, 영업하고, 정산받는 플랫폼**입니다.
쓰는 사람이 세 종류예요.

| 사용자 | 하는 일 | 비유 |
|---|---|---|
| 방문자(소비자) | 상품 구경, 가입 | 백화점에 그냥 온 손님 |
| 부업 파트너 | 상품 학습·영업·정산 | 백화점에 입점한 판매원 |
| 운영자(어드민) | 상품·파트너 관리 | 백화점 관리사무소 직원 |

세 사람이 필요로 하는 화면과 보안 수준이 완전히 다릅니다.
이 "다름"을 어떻게 나누고 어떻게 공유했는가 — 그게 이 프로젝트 설계의 핵심 주제예요.

## 1. 왜 "모노레포 + 두 개의 프레임워크"인가

### 1-1. 모노레포가 뭐예요?

**모노레포(monorepo)** = 여러 개의 앱·라이브러리를 **하나의 깃 저장소(폴더)** 안에서 관리하는 방식입니다.

반대는 **멀티레포(폴리레포)** — 앱마다 저장소를 따로 두는 방식이고요.

```text
여기쏘 저장소 (하나)
├── apps/web       ← 소비자·파트너용 사이트
├── apps/admin     ← 운영자용 관리 화면
└── packages/
    ├── design-system     ← 공통 디자인 부품
    └── database-types     ← DB 스키마 타입
```

비유하자면, **집 한 채 안에 방(앱)이 여러 개** 있고, 거실·주방(공통 부품)은 모두가 같이 쓰는 구조입니다. 방을 각각 다른 건물에 지으면(멀티레포) 주방을 쓰려고 매번 옆 건물까지 걸어가야 하죠.

**왜 좋은가**
- 공통 부품(디자인, DB 타입)을 한 곳에 두고 모두가 즉시 씁니다. 복붙·버전 어긋남이 사라져요.
- 여러 앱을 한 번에 고치는 변경(예: 버튼 디자인 통일)을 **하나의 PR**로 처리합니다.

**대안과 비교**

| 방식 | 장점 | 단점 | 여기쏘 선택 이유 |
|---|---|---|---|
| 멀티레포(앱마다 저장소) | 앱별 독립성 최고, 권한 분리 쉬움 | 공통 코드 공유가 고통(npm 배포·버전 관리) | 혼자/소규모라 공유 이득이 훨씬 큼 |
| **모노레포(선택)** | 공통 코드 즉시 공유, 일괄 변경 쉬움 | 저장소가 커지고 빌드 관리 필요 | Turborepo로 빌드 관리 해결 |

### 1-2. pnpm + Turborepo는 왜?

- **pnpm** = 패키지(라이브러리) 설치 도구. npm/yarn의 형제인데, 같은 라이브러리를 앱마다 중복 저장하지 않고 **한 번만 저장해서 링크**합니다. 그래서 디스크·설치가 빠르고, 모노레포의 "워크스페이스"(여러 앱 묶음)를 잘 지원해요.
- **Turborepo** = 모노레포 빌드 **가속기**. "이미 빌드한 건 또 안 한다(캐시)", "안 바뀐 앱은 건너뛴다"를 해줍니다.

비유: pnpm은 **공용 창고**(라이브러리를 한 번만 쌓아두고 방마다 연결), Turborepo는 **작업 반장**(안 바뀐 일은 다시 안 시킴)이에요.

> 대안: npm/yarn workspaces도 가능. 다만 설치 효율(pnpm)과 캐시 빌드(Turborepo)를 따로 챙기면 큰 모노레포일수록 체감이 큽니다.

### 1-3. 진짜 핵심 결정 — 왜 web은 Next.js, admin은 Vite로 "갈랐나"

이게 이 프로젝트에서 가장 설명할 가치가 큰 판단입니다.
**"둘 다 리액트인데 왜 프레임워크를 다르게 썼냐"**는 질문이 반드시 나와요.

먼저 두 앱의 요구가 다릅니다.

| | apps/web (소비자·파트너) | apps/admin (운영자) |
|---|---|---|
| 누가 봄 | 불특정 다수, 검색엔진도 봄 | 소수의 내부 직원만 |
| 중요한 것 | **첫 화면 빠르게 + SEO(검색 노출)** | 로그인 뒤 기능 밀도 |
| 성격 | 공개 웹사이트 | 사내 도구(대시보드) |

- **Next.js (web에 사용)**: **서버에서 HTML을 미리 만들어 보내주는(SSR/서버 컴포넌트)** 기능이 강점. 그래서 첫 화면이 빠르고, 구글 같은 검색엔진이 내용을 잘 읽어 **SEO에 유리**합니다. 공개 사이트에 딱 맞아요.
- **Vite + React (admin에 사용)**: 브라우저에서 자바스크립트로 화면을 그리는 **SPA(단일 페이지 앱)**. SEO가 필요 없는 **로그인 뒤 내부 도구**라면, 서버 렌더링의 복잡함을 짊어질 이유가 없습니다. Vite는 **개발 중 새로고침이 극도로 빠른** 게 강점이라 내부 도구 개발 속도가 좋아요.

**한 줄 논리**: "공개해서 검색에 걸려야 하는 곳(web)엔 서버 렌더링(Next), 로그인 뒤 우리끼리 쓰는 도구(admin)엔 가볍고 빠른 SPA(Vite)." **필요가 다르니 도구도 다르게** 쓴 것이고, 대신 디자인·DB 타입은 공유해서 중복은 없앴습니다.

**대안 비교**

| 대안 | 왜 안 골랐나 |
|---|---|
| 둘 다 Next.js | admin에는 SSR·SEO가 필요 없는데 그 복잡도를 떠안게 됨. Vite의 빠른 개발 경험도 포기 |
| 둘 다 Vite(SPA) | web의 SEO·첫 로딩을 포기하게 됨. 공개 서비스에 치명적 |
| **web=Next / admin=Vite (선택)** | 각 앱의 진짜 요구에 최소 복잡도로 맞춤. 공통은 패키지로 공유 |

> 면접 포인트: "프레임워크를 통일하지 않은 건 유행이 아니라 **각 앱의 요구(SEO 유무, 사용자 범위)**에서 역산한 결정"이라고 답하면 강합니다.

### 1-4. 나머지 스택 한눈에

| 기술 | 쉬운 설명 | 왜 이걸? | 대안 |
|---|---|---|---|
| React 19 + App Router | 화면 만드는 기본 틀. 서버 컴포넌트로 서버에서 그림 | 첫 로딩·SEO 확보, 상호작용 부분만 브라우저로 | Pages Router(구식), Remix 등 |
| Route Handler(BFF) | Next 안에 만든 미니 서버(API) | **별도 백엔드 서버 없이** 서버 로직 처리 | 별도 Node/Nest 서버(운영 부담↑) |
| Supabase | 관리형 Postgres DB + 인증 + 파일 | DB·인증·보안을 한 번에, 서버 운영 부담↓ | 직접 세운 Postgres+백엔드(할 일↑) |
| Vercel | 배포 플랫폼 | Next와 궁합 최고, 미리보기 배포 자동 | AWS 직접 구성(복잡) |
| TypeScript + Biome | 타입 검사 + 린트/포맷 도구 | 실수를 컴파일 때 잡고, 코드 스타일 통일 | ESLint+Prettier(더 느리고 설정 많음) |

**BFF(Backend For Frontend)** 개념만 짚고 갈게요. "프론트를 위한 백엔드"라는 뜻인데, Next.js 안의 `app/api/*` 폴더에 서버 코드를 두면 **프론트엔드 프로젝트 안에 필요한 만큼의 서버**가 같이 사는 셈입니다. 별도 서버를 세우고 운영·배포하는 부담이 사라지죠. 규모가 작고 팀이 작을 때 특히 이득입니다.

## 2. 폴더 구조와 화면 나누기 — "왜 이렇게 잘게 쪼갰나"

### 2-1. Layout(껍데기) / View(내용) 분리

Next.js에서 `app/` 폴더는 **URL 주소(라우팅)**를 담당합니다.
그런데 여기쏘는 `app/`을 **아주 얇게** 유지하고, 실제 화면은 다른 곳에 뒀어요.

```text
app/(sidejob)/layout.tsx  →  <SidejobShell>{children}</SidejobShell>   // 주소·틀만
shells/SidejobShell/      →  헤더(GNB) + 스크롤 영역           // 공통 껍데기
app/support/page.tsx      →  <SupportView />                    // "이 주소는 이 화면" 연결만
views/SupportView/        →  실제 화면 조립                     // 진짜 내용
```

**왜 나눴나 (SRP: 단일 책임 원칙)**
"주소가 바뀌는 이유"와 "화면 내용이 바뀌는 이유"는 서로 다릅니다.
한 파일이 둘 다 하면, 주소 하나 고치려다 화면을 건드리고 화면 고치려다 주소를 건드려요.
그래서 **주소 담당(app) / 껍데기 담당(shells) / 내용 담당(views)**로 역할을 갈랐습니다.

비유: **택배 시스템**과 같아요. 주소지(app)는 "어디로 보낼지"만, 상자(shell)는 "어떻게 포장할지"만, 내용물(view)은 "무엇을 담을지"만 신경 씁니다. 주소를 바꿔도 내용물은 그대로죠.

### 2-2. 실전 버그 하나로 이해하는 "Shell(앱 셸) 패턴"

이 부분이 문서에서 가장 값진 실전 사례예요. 면접에서 스토리로 쓰기 좋습니다.

**문제 상황**: 부업 카테고리 탭을 눌러 페이지를 옮길 때마다(`/` ↔ `/sidejob/무엇`), 상단 메뉴(GNB)의 "현재 위치 표시 막대(인디케이터)"가 **매번 0 위치에서 다시 그려지며 튀는** 버그가 있었습니다.

**원인**: 헤더를 **각 페이지가 직접** 그리고 있었어요. 그러니 페이지를 옮길 때마다 헤더도 통째로 새로 태어나고(리마운트), 헤더가 기억하던 "막대 위치" 정보가 매번 초기화된 거죠.

비유: 방을 옮길 때마다 **거실 시계까지 새로 사 오는** 상황. 옮기는 건 방(페이지)인데 거실(헤더)까지 리셋된 거예요.

**해결**: 헤더를 페이지가 아니라 **라우트 그룹 레이아웃(SidejobShell)**으로 끌어올렸습니다. 그러면 주소가 바뀌어도 껍데기(헤더)는 그대로 살아있고 **내용(children)만 교체**됩니다. 시계는 거실에 계속 두고, 방 안 물건만 바꾸는 거예요.

> 배운 것: 앱 셸 패턴은 결국 **"어떤 UI가 페이지 경계를 넘어 살아남아야 하는가"**를 정하는 설계 문제였다 — 이게 결론입니다.

### 2-3. 사이드바 레이아웃과 `min-w-0`의 비밀

화면 왼쪽에 고정 폭 사이드바, 오른쪽에 늘어나는 콘텐츠 — 이걸 CSS flex로 만듭니다.
`고정 px(사이드바) + flex-1(콘텐츠)` 구조예요.

여기서 초심자를 잘 무는 함정이 하나 있습니다: **`min-w-0`**.
flex 항목은 기본적으로 "내용물보다 작게는 안 줄어드는"(min-width: auto) 성질이 있어요.
그래서 콘텐츠 안에 긴 표나 텍스트가 있으면 칸이 안 줄고 **가로 스크롤**이 생깁니다.
`min-w-0`을 주면 "내용물보다 작아져도 된다"가 되어 정확히 신축합니다.

비유: **고무줄 바지**인데 안쪽에 철사가 들어 있어 안 줄어드는 상태. `min-w-0`이 그 철사를 빼주는 것.

### 2-4. 폴더를 "쓰는 범위만큼만" 가까이 둔다 (LCA 규칙)

파일(컴포넌트·훅 등)을 **실제로 쓰이는 가장 가까운 위치**에 둡니다.

- 한 화면에서만 쓰면 → 그 화면 폴더 안에
- 형제 화면 둘이 나눠 쓰면 → 한 단계 위 `shared/`로
- 앱 전체가 쓰면 → 최상위 `components`·`hooks`로 승격

비유: 물건을 **쓰는 방에 두는 정리 원칙**. 나 혼자 쓰는 칫솔은 내 방에, 온 가족이 쓰는 청소기는 창고에. 아무거나 다 창고(전역)에 넣으면 창고가 터지고 뭐가 뭔지 몰라요.

또 하나: **컴포넌트 300줄 규칙**. 한 파일이 300줄을 넘으면 하위 컴포넌트·커스텀 훅·데이터 파일로 쪼갭니다. 파일이 너무 길면 읽기도, 고치기도, 재사용하기도 어렵거든요.

> 대안: 처음부터 모든 걸 전역 `components`에 몰아두는 방식 — 초반엔 편하지만 커지면 "이거 어디서 쓰지? 지워도 되나?"를 아무도 모르게 됩니다. **범위를 좁게 두면 안전하게 지우고 옮길 수 있어요.**

## 3. 인증·데이터베이스·보안 — 가장 중요한 부분

### 3-1. 먼저 용어부터: 인증 / 인가 / 세션 / 토큰

- **인증(Authentication)** = "너 누구야?"를 확인 (로그인)
- **인가(Authorization)** = "너 이거 봐도 돼?"를 확인 (권한)
- **세션(Session)** = 로그인한 상태를 서버가 기억하는 것
- **토큰(Token)** = "나 로그인한 사람이야"를 증명하는 **디지털 출입증**

비유: 클럽에 들어갈 때 신분증 확인(인증) → 손목 밴드 채워줌(토큰/세션) → VIP룸은 밴드 색으로 막음(인가).

### 3-2. 왜 인증을 "두 종류"로 나눴나 (이중 인증 구조)

여기쏘는 **의도적으로** 로그인 방식을 두 가지로 나눴습니다. 이게 핵심 어필 포인트예요.

| 대상 | 로그인 방식 | 왜? |
|---|---|---|
| 소비자·파트너(web) | **카카오/네이버 소셜 로그인** → 직접 만든 JWT | 일반 사용자는 "카카오로 3초 로그인"이 안 되면 이탈함. UX가 생명 |
| 운영자(admin) | **Supabase Auth(이메일+비밀번호)** | 소수 내부 직원. 화려한 UX 불필요, 검증된 표준 인증이면 충분 |

**한 줄 논리**: "많은 일반 사용자에겐 편한 소셜 로그인, 소수 내부자에겐 튼튼하고 단순한 표준 로그인." **각 대상에 최소 복잡도의 인증**을 붙인 겁니다.

**대안 비교**

| 대안 | 문제 |
|---|---|
| 전부 Supabase Auth로 통일 | 소셜 로그인 UX를 원하는 대로 세밀하게 못 만듦. 일반 사용자 이탈 위험 |
| 전부 커스텀 JWT로 통일 | 운영자 로그인까지 직접 보안 관리 → 굳이 바퀴를 다시 발명, 위험만 늘어남 |
| **대상별로 분리(선택)** | 각자에게 맞는 방식. 대신 코드에서 파일을 확실히 분리해 관리 |

### 3-3. 커스텀 JWT를 안전하게 만든 방법

**JWT**(JSON Web Token)는 서버가 발급하는 **위조 방지 출입증**입니다. 안에 "이 사람은 누구, 언제까지 유효" 같은 정보가 들어 있고, 서버만 아는 **비밀 열쇠로 서명**돼 있어 남이 못 바꿉니다.

여기쏘는 `jose`라는 라이브러리로 이 토큰을 검증하는데, 두 가지 보안 장치가 핵심입니다.

```js
const { payload } = await jwtVerify(token, secret, {
  algorithms: ['HS256'],       // (1) 서명 방식 고정
  audience: SESSION_AUDIENCE,  // (2) 이 토큰의 용도 고정
});
```

- **(1) `algorithms: ['HS256']` — 서명 방식 고정**
  JWT에는 "이 토큰을 어떤 방식으로 검증하라"는 칸이 있는데, 공격자가 이 칸을 "검증 안 함(none)"으로 바꿔 위조하는 **알고리즘 혼동 공격**이 유명합니다. 허용 방식을 딱 하나로 못박아 이 공격을 막습니다.
  비유: 위조범이 "이 문은 그냥 밀면 열려"라고 안내판을 바꿔치기 못 하게, 열쇠 종류를 하나로 고정.

- **(2) `audience` — 토큰 용도 고정**
  여기쏘엔 토큰이 두 종류예요. "로그인 세션용"과 "휴대폰 인증용". 만약 용도 검사를 안 하면, 휴대폰 인증용 토큰을 로그인용으로 **재활용**하는 악용이 가능합니다. `audience`(청중/용도)를 검사해서 **용도가 맞는 토큰만** 통과시킵니다.
  비유: 놀이공원 자유이용권과 주차권은 둘 다 "티켓"이지만 서로 못 씁니다. 용도 표시를 확인하는 것.

추가로 쿠키(출입증을 브라우저에 보관하는 방식)에도 보안을 겁니다.

| 설정 | 뜻 | 막는 것 |
|---|---|---|
| `httpOnly` | 자바스크립트가 쿠키를 못 읽음 | 악성 스크립트의 토큰 탈취(XSS) |
| `secure`(운영) | HTTPS에서만 전송 | 중간에서 엿보기 |
| `sameSite=lax` | 다른 사이트발 요청엔 안 붙음 | 위장 요청(CSRF) |

그리고 소셜 로그인 시작 시 쓰는 CSRF 방지용 `state` 값을 **카카오/네이버 각각 다른 쿠키**(`oauth_state_kakao`/`oauth_state_naver`)에 저장합니다. 두 개를 동시에 로그인하려 해도 서로 덮어쓰지 않게요.

### 3-4. RLS — 보안을 "데이터베이스에게" 맡기다

**RLS(Row Level Security, 행 수준 보안)**는 Postgres 데이터베이스의 기능으로, **"이 사람은 이 행(row)을 봐도 되는지"를 DB가 직접 판단**하게 합니다.

```sql
-- 이 표에 행 단위 보안을 켠다
alter table public.phone_product_color_images enable row level security;

-- 익명 사용자는 '공개된' 행만 읽을 수 있다
create policy "public read visible ..." for select to anon using (/* visible */);

-- 로그인한 운영자는 읽고 쓰기 다 가능
create policy "authenticated write ..." for all to authenticated using(true) with check(true);
```

**왜 이게 좋은가**
보통은 "이 사람이 이 데이터 봐도 되나?"를 **앱 코드(서버)에서** 매번 검사합니다. 그런데 앱에 API가 100개면 100군데에 검사를 넣어야 하고, 한 군데라도 빠뜨리면 그게 보안 구멍이에요.
RLS는 그 검사를 **데이터가 사는 DB 자체에** 붙입니다. 그러면 **어느 문으로 들어오든** 규칙이 적용돼요. 검사를 깜빡할 수가 없습니다.

비유: 앱에서 검사 = **각 방문마다 경비원이 신분 확인**(경비원이 실수하면 뚫림). RLS = **금고 자체가 지문을 인식**(어느 손이 열려 해도 금고가 판단).

**주의점 하나**: web 서버는 `service_role`이라는 **마스터 키**로 DB에 접근해서 RLS를 우회합니다(서버는 신뢰된 존재라서). 대신 이 마스터 키를 쓰는 코드와 일반 사용자(anon) 코드를 **파일 단위로 확실히 분리**해서, 마스터 키가 브라우저로 새어나가지 않게 합니다. 이게 안 되면 그냥 다 뚫려요.

| 접근 주체 | 사용하는 키 | 권한 |
|---|---|---|
| 브라우저의 일반 사용자 | anon(공개 키) | RLS 규칙대로 공개된 것만 |
| web 서버 내부 로직 | service_role(마스터 키) | 전체 접근(대신 서버 밖으로 노출 금지) |
| 운영자 로그인 | authenticated | RLS 규칙대로 쓰기 허용 |

### 3-5. 입력 검증 — Zod 대신 "공용 순수 함수"

사용자가 입력한 값(닉네임 등)은 **믿으면 안 됩니다.** 항상 검사해야 해요.

많은 프로젝트가 **Zod** 같은 "스키마 검증 라이브러리"를 씁니다. 여기쏘는 그 대신 **직접 만든 공용 검증 함수**를 택했어요.

**왜?** 클라이언트(입력 폼)와 서버(API)가 **똑같은 규칙**을 공유해야 하기 때문입니다. 공용 순수 함수 하나를 양쪽이 같이 import하면, "닉네임 규칙"이 한 곳에만 존재하게 됩니다. 규칙이 바뀌어도 한 군데만 고치면 되고, 앞뒤가 어긋날 일이 없어요.

```js
const session = token ? await verifySession(token) : null;        // 없으면 401
if (current.status === 'active') return { ok: true };             // 이미 됐으면 그냥 성공(멱등)
const nickname = String(body?.nickname ?? '').trim();            // 무슨 값이 와도 문자열로 강제
if (validateNickname(nickname) !== 'valid') return ..., { status: 400 }; // 공용 규칙 위반 시 400
```

여기서 배울 두 가지 방어 기술:

- **`String(body?.x ?? '')` 방어적 강제**: 사용자가 숫자·null·이상한 값을 보내도 일단 **문자열로 바꾸고** `.trim()` 합니다. 그래야 "숫자엔 trim이 없어요" 같은 에러로 서버가 터지지 않고, 항상 일관되게 검사할 수 있어요.
  비유: 무엇이 들어오든 **입구에서 규격 상자에 담아** 처리하는 것.

- **상태 코드 규약**: 로그인 안 됨 = **401**, 값이 틀림 = **400**, 권한 없음 = **403**. 이 약속을 프로젝트 전체가 지키면, 에러만 봐도 뭐가 문제인지 바로 압니다.

- **멱등(idempotent)**: "같은 요청을 여러 번 해도 결과가 같다"는 성질. 온보딩(가입 마무리)을 여러 번 눌러도, 이미 완료(active)면 그냥 "성공"을 돌려줍니다. 중복 클릭·재시도로 데이터가 꼬이지 않아요.
  비유: 엘리베이터 버튼을 열 번 눌러도 한 번 부른 것과 결과가 같은 것.

> 대안 비교: **Zod**는 강력하고 편합니다(특히 복잡한 데이터). 다만 여기쏘는 규칙이 단순하고 **클라·서버 공유**가 최우선이라, 라이브러리 없이 순수 함수로 가볍게 간 것. "규모가 커지면 Zod로 바꿀 수 있다"고 답하면 균형 잡힌 답변입니다.

### 3-6. 마이그레이션 — DB 구조 바꾸는 규칙

**마이그레이션(migration)** = 데이터베이스의 구조(표, 컬럼)를 바꾼 **기록 파일**입니다. "몇 월 며칠에 이 표에 이 칸을 추가했다"가 파일로 남아요.

여기쏘의 규칙: **파일 작성 → 깃 커밋 → `supabase db push` 로만 반영**(현재 34개). SQL 편집기에서 직접 손대는 건 금지입니다.

**왜?** DB를 손으로 직접 바꾸면, **코드(파일)에 적힌 구조**와 **실제 원격 DB의 구조**가 서로 달라지는 **드리프트(drift, 어긋남)**가 생깁니다. 그러면 "내 컴퓨터에선 됐는데 배포하면 안 돼요" 사태가 나요. 그리고 web·admin이 **같은 개발 DB를 공유**하므로, 한 사람이 몰래 바꾸면 다른 사람이 영문도 모르고 깨집니다.

비유: 공사 도면(파일) 없이 현장에서 벽을 막 뚫으면, 도면과 실제 건물이 달라져서 다음 사람이 사고 납니다. **모든 변경은 도면부터 고치고 그대로 시공**하는 규율이에요. 이미 적용된 파일은 수정하지 않고 **새 변경(ALTER)을 이어 붙입니다**(과거 기록 보존).

## 4. 핵심 비즈니스 흐름 & URL 설계

### 4-1. 소셜 로그인 → 가입 마무리 → 활성화 (2단계 상태)

가입 과정을 그림으로 풀면 이렇습니다.

```text
소셜 로그인 시작(카카오/네이버, CSRF state 발급)
   ↓
콜백: state 대조 + 코드 교환으로 사용자 확인
   ↓
users 테이블에 저장(상태 = pending_profile) + 세션 발급   ← 아직 "반쪽 가입"
   ↓
휴대폰 인증(전용 phoneToken 발급)
   ↓
온보딩 API에서 닉네임 등 검증
   ↓
상태 = active   ← 이제 "진짜 파트너"
```

핵심은 **상태를 2단계로 나눈 것**(`pending_profile` → `active`)입니다.

**왜?** "카카오 로그인만 하고 정보 입력은 안 끝낸 사람"과 "가입을 완전히 마친 파트너"를 구분하기 위해서예요. `active`인 사람만 진짜 로그인으로 취급합니다. 안 그러면 가입을 덜 끝낸 사람에게 **파트너 전용 화면이 새어나갈** 수 있거든요.

비유: 회원가입 이메일 인증과 같아요. 가입 버튼만 누른 상태(pending)와 인증까지 끝낸 상태(active)를 구분해야, 미완성 계정이 회원 혜택을 못 챙기죠.

### 4-2. 파트너 등급 계산과 "요청 한 번만" 최적화

파트너 등급은 **최근 3개월 실적**으로 계산합니다. 그런데 한 화면에 이 등급을 보여주는 곳이 여러 군데면, 순진하게 짜면 **같은 데이터를 여러 번** 서버에 물어봐요.

여기쏘는 **모듈 캐시 + 구독 + 진행 중 요청 중복 제거**(`useSyncExternalStore`)로 여러 곳이 등급을 필요로 해도 **서버 요청은 딱 한 번**만 나가게 했습니다. 그리고 비로그인 확정 화면에서는 아예 요청을 **차단**해서, 필요 없는 호출을 안 합니다.

비유: 사무실에서 다섯 명이 "오늘 날씨?" 물어볼 때, 한 명이 대표로 한 번 확인하고 **모두에게 공유**하는 것. 다섯 번 밖에 나가 확인하지 않아요.

### 4-3. URL을 역할별로 나눈 설계

주소(URL)에 정보를 어떻게 담느냐도 설계입니다. 여기쏘는 목적에 따라 방식을 나눴어요.

| 목적 | 방식 | 예시 | 쉬운 설명 |
|---|---|---|---|
| **무엇을** 가리키나(리소스) | 경로 변수(Path) | `/phones/[id]`, `/sidejob/[category]` | 대상 그 자체를 주소에 |
| 어떻게 **거르나**(조회·필터) | 쿼리(Query) | `?carrier=kt`, `?sort=latest` | 같은 목록을 다르게 보기 |
| 화면 **묶기**(레이아웃) | 라우트 그룹 | `app/(sidejob)/` (주소엔 안 보임) | 헤더 공유용, URL엔 영향 없음 |

**왜 이렇게?**
- 탭 상태(어느 카테고리를 보는지)를 **경로 변수**에 실으면, 새로고침·뒤로가기·링크 공유가 **저절로** 동작합니다. 주소 자체가 "지금 이 화면"을 담고 있으니까요.
- 정렬·필터처럼 "같은 목록의 다른 보기"는 **쿼리**가 맞습니다. `?sort=latest`처럼요.
- **라우트 그룹**(`(sidejob)`)은 URL에 안 나타나면서 여러 페이지가 **같은 헤더를 공유**하게 해줍니다 — 앞의 2-2 인디케이터 버그 해결과 바로 연결되는 도구예요.

비유: 경로 변수는 **책의 제목**(그 책을 딱 가리킴), 쿼리는 **정렬 옵션**(같은 책장을 가격순/최신순으로), 라우트 그룹은 **책장 뒤 공용 선반**(독자에겐 안 보이지만 여러 책이 같이 씀).

## 5. 성능 최적화 · 타입스크립트 · 디자인 시스템

이 부분은 "화면이 부드럽게, 코드가 안전하게, 디자인이 일관되게"를 위한 디테일들이에요. 입문자에게 조금 어려운 개념이라 비유를 많이 넣었습니다.

### 5-1. "참조 동일성"으로 화면 튐 막기 (조금 어려운 파트)

리액트에는 함정이 하나 있어요. 컴포넌트가 다시 그려질 때, 안에서 만든 **함수도 매번 새로 태어납니다.** 겉보기엔 같은 함수인데 리액트는 "새 함수네?"라고 봐요(참조가 다름).

이게 왜 문제냐면, 스크롤·바깥 클릭을 감지하는 코드(`useEffect`)가 "함수가 바뀌었네" 하고 **감시를 껐다 켰다 반복**합니다. 그러면 애니메이션이 중간에 튀어요.

- 해결책 **`useCallback`**: 함수를 "새로 만들지 말고 **이전 것 재사용**해"라고 고정하는 도구. 그러면 감시가 불필요하게 재등록되지 않습니다.
  비유: 매번 명함을 새로 파지 말고 **같은 명함을 계속 쓰는** 것. 상대가 "연락처 또 바뀌었네?" 하며 헷갈리지 않아요.

- GNB 인디케이터(위치 막대)는 크기 변화를 감지하는 코드가 "현재 탭"에 자꾸 다시 매달려 튀는 문제가 있었어요. 그래서 현재 탭 값을 **ref(다시 그리기를 안 유발하는 저장소)**로 읽고, "크기 변화 감지"와 "탭 전환" 로직을 **서로 분리**했습니다.
- "**안 보이는 동안에만 위치를 점프**"(visibleRef) 기법으로, 빠르게 연속 클릭할 때 막대가 가로로 튀는 것도 없앴습니다.

> 초심자 요약: 리액트에서 "매번 새로 태어나서 생기는 불필요한 재작동"을 막는 게 핵심 최적화 주제. 도구는 `useCallback`(함수 고정), `ref`(조용한 저장소)예요.

### 5-2. 문자열·주소 다루기 안전장치

- `split('/').filter(Boolean)` — 주소를 `/`로 자를 때 생기는 **빈 조각을 제거**. 예: `/a/b/`를 자르면 `['', 'a', 'b', '']`처럼 빈 칸이 생기는데 이걸 걸러냅니다.
- 주소 정보를 읽을 때 `useParams` 대신 **`usePathname`에서 계산**. 특정 상황(pushState 전환)에서 `useParams`가 옛날 값으로 남는 버그를 피하려고요.
- 서버로 들어온 값은 항상 `String()`으로 강제(3-5에서 본 방어 기술).

### 5-3. 타입스크립트 컨벤션(약속)

| 약속 | 내용 | 왜 |
|---|---|---|
| 데이터 구조는 `type` 사용 | `interface` 대신 `type` | 팀 내 스타일 통일, 일관성 |
| props 타입 이름은 항상 `Props` | 컴포넌트 속성 타입명 규칙 | 어디서든 바로 알아봄 |
| `noUnusedLocals/Parameters` | 안 쓰는 변수는 **컴파일 에러** | 죽은 코드가 안 쌓임(`_` 접두사만 예외) |

**`strict` 모드**란 타입스크립트를 **엄격 모드**로 켜는 것. 실수 가능성이 있는 코드를 컴파일 단계(코드 돌리기 전)에서 잡아줍니다. 비유: **맞춤법 검사기를 최고 민감도로** 켜둔 것. 오타를 제출 전에 다 잡아줘요.

### 5-4. Tailwind CSS 규칙

- 조건부 클래스는 **`cn()`**(clsx + tailwind-merge)으로 병합. 서로 충돌하는 클래스(`p-2`와 `p-4`)를 똑똑하게 정리해줍니다.
- 반응형 기준을 **1024px(lg:) 하나**로 통일. 기준점이 여러 개면 관리가 복잡해지니 단순화한 것.
- 카드 폭 비율은 `grid-cols-[612fr_396fr]`처럼 **grid의 fr 단위로 정확히 고정**. flex의 `flex-grow`는 시작 크기가 다르면 비율이 어긋나서, 정확한 비율엔 grid가 맞습니다.

비유: flex는 "대충 남는 공간 나눠 갖기", grid의 fr은 "612:396으로 **정확히** 나누기". 디자인 시안을 픽셀까지 맞출 땐 grid.

### 5-5. 디자인 시스템 — 부품을 표준화하다

**디자인 시스템(DS)** = 버튼·입력창·카드 같은 UI 부품과 색·간격 같은 **디자인 토큰**을 한 곳(`packages/design-system`)에 모아 **모든 앱이 재사용**하는 것. 50여 개 부품이 들어 있어요.

**왜?** 앱마다 버튼을 따로 만들면 색·모양이 제각각이 되고, 하나 바꾸려면 여러 곳을 고쳐야 합니다. DS에 한 번 만들어두면 **모두가 같은 버튼**을 쓰고, 한 번 고치면 전부 반영돼요.

비유: **레고 블록 세트**. 매번 블록을 깎아 만들지 않고, 표준 블록을 조립합니다. 그리고 Figma(디자인 툴) 수치를 **눈대중이 아니라 도구로 정확히 읽어** 구현하고, 실제 렌더와 대조합니다.

## 6. 개발 생산성 & 협업 전략

혼자 하든 팀이든, "실수를 자동으로 막고, 변경을 안전하게 합치는" 장치들입니다.

### 6-1. 커밋 전 단일 관문 — `check-all`

```json
"check-all": "turbo run type-check lint --continue"
"knip": "knip"
```

코드를 커밋(저장)하기 전에 **타입 검사 + 린트(문법·스타일 검사)**를 한 번에 돌립니다. `--continue`는 하나가 실패해도 멈추지 않고 **끝까지 검사해 전체 문제를 한눈에** 보여줘요.

**미사용 코드(죽은 코드) 3단 분업**(ADR-0001에 기록):

| 무엇을 잡나 | 도구 |
|---|---|
| 안 쓰는 변수·파라미터 | TypeScript |
| 안 쓰는 import | Biome |
| 안 쓰는 파일·export·의존성 | Knip |

비유: **출국 전 3중 검색대**. 각 검색대가 다른 걸 잡아, 쓰레기 코드가 프로젝트에 남지 않게 합니다.

배포는 앱별 워크플로로 나눠서, **개발용(preview)**과 **운영용(production)** 환경의 비밀값(시크릿)을 섞이지 않게 격리합니다. 새 환경변수는 코드(`env.d.ts`)와 Vercel **양쪽에 등록**하는 규칙이에요.

### 6-2. PR과 깃 전략

**PR(Pull Request)** = "내가 이렇게 고쳤어요, 합쳐도 될까요?"라고 올리는 **변경 제안서**입니다.

| 규칙 | 내용 | 왜 |
|---|---|---|
| 독립 PR(쌓기 지양) | 항상 최신 main에서 새로 분기 | PR끼리 얽히면 리뷰·병합이 지옥이 됨 |
| **1,000줄 이하** | 넘을 것 같으면 미리 쪼갬 | 큰 PR은 리뷰가 부실해지고 버그를 놓침 |
| 본문 템플릿 고정 | 리뷰어가 볼 지점 명시 | 리뷰 품질·속도↑ |
| 리뷰 우선순위 P1/P2/P3 | 중요도 표시 | 뭘 먼저 고칠지 명확 |

특히 좋은 습관 두 가지:
- **지적이 정확하면 그냥 고치는 게 아니라, 실제로 재현·계측해서 확인한 뒤 반영**하고, 커밋에 어느 PR의 어느 지적인지 기록(`fix(ds): … (PR #210 P3)`). 나중에 "이건 왜 고쳤지?"의 답이 코드에 남습니다.
- push 전 `reset --soft/--mixed`로 커밋을 **논리 단위로 재구성**. "오타 수정 → 되돌림 → 또 수정" 같은 지저분한 기록 대신, "기능 A 추가" 하나로 깔끔하게 정리해 올립니다.

비유: 보고서를 여러 번 고쳐 쓴 흔적을 다 남기지 말고, **최종본을 깔끔한 목차로** 제출하는 것.

### 6-3. ADR — 결정을 기록으로 남기다

**ADR(Architecture Decision Record)** = "우리가 왜 이 기술을 골랐고, 어떤 대안을 포기했는지"를 적어 `docs/decisions/`에 남기는 문서입니다.

**왜?** 6개월 뒤의 나(또는 새 팀원)는 "왜 Zod 안 쓰고 직접 만들었지?"를 기억 못 합니다. ADR이 있으면 **결정의 이유와 포기한 선택지**가 그대로 남아, 같은 고민을 반복하거나 함부로 되돌리지 않아요.

비유: **판례**와 같아요. 왜 이렇게 판단했는지 근거를 남겨두면, 다음 사람이 그 위에서 판단할 수 있습니다.

## 마무리: 이 프로젝트를 한 문장으로 관통하는 원칙

이 아키텍처 전체를 꿰뚫는 생각은 하나예요:

> **"서로 다른 것은 다르게 나누되, 같은 것은 철저히 공유한다.
> 그리고 모든 결정에는 포기한 대안과 그 이유가 있다."**

- 나누기: 사용자(방문자/파트너/운영자), 프레임워크(Next/Vite), 인증(소셜 JWT/Supabase), 책임(주소/껍데기/내용)
- 공유하기: 디자인 시스템, DB 타입, 검증 규칙(공용 함수)
- 근거 남기기: ADR, 커밋에 PR 참조, 마이그레이션 파일 이력

면접에서든 회고에서든, 각 기술을 "유행이라서"가 아니라 **"이 요구 때문에, 이 대안 대신 골랐다"**로 설명할 수 있다는 게 이 프로젝트의 진짜 강점입니다.

   → "일반 사용자는 소셜 로그인 UX가 이탈을 좌우해 커스텀 JWT로 세밀하게, 소수 운영자는 검증된 Supabase Auth로 단순하게. 대상별 최소 복잡도입니다."

4. **Zod 안 쓰고 왜 직접 검증?**
