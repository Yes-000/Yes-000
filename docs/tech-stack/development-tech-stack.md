## 1. 기술 스택이란?

**기술 스택(technology stack)**은 하나의 서비스나 애플리케이션을 만들고 운영하는 데 함께 사용하는 프로그래밍 언어, 프레임워크, 라이브러리, 데이터베이스, 배포 도구 등의 조합입니다.

웹 서비스를 식당에 비유하면 다음과 같아요.

- **프론트엔드**: 손님이 보는 메뉴판과 식당의 홀
- **백엔드**: 주문을 받아 처리하고 주방에 전달하는 직원
- **데이터베이스**: 재료와 주문 기록을 보관하는 창고·장부
- **배포 플랫폼**: 식당을 손님이 방문할 수 있도록 문을 열고 운영하는 장소
- **프로그래밍 언어와 프레임워크**: 이 모든 것을 만들 때 사용하는 도구와 작업 방식

예를 들어 `React + TypeScript + Node.js + PostgreSQL`이라고 하면, 화면은 React로 만들고 TypeScript로 코드의 형태를 점검하며, 서버는 Node.js로 실행하고, 데이터는 PostgreSQL에 저장하는 조합을 뜻합니다.

### 스택을 고를 때 생각할 것

1. **무엇을 만들지**: 검색 노출이 중요한 공개 사이트인지, 로그인 후 쓰는 관리 도구인지
2. **누가 만들고 운영할지**: 혼자 만드는지, 팀이 유지보수하는지
3. **필요한 기능과 품질**: 성능, 보안, 접근성, 확장성, 오프라인 지원 등이 필요한지
4. **팀의 경험과 생태계**: 팀이 이미 잘 아는 기술인지, 필요한 라이브러리와 문서가 충분한지
5. **운영 비용과 복잡도**: 서버와 데이터베이스를 직접 관리할 역량이 있는지

가장 인기 있는 기술이 항상 정답은 아닙니다. 현재 요구를 만족하면서 팀이 안전하게 만들고 운영할 수 있는 조합이 좋은 스택입니다.

## 2. 프로그래밍 언어와 버전 변천사

### 언어와 프레임워크는 다른 것

- **프로그래밍 언어**는 컴퓨터에 작업을 지시하는 문법과 규칙입니다. 예: JavaScript, TypeScript, Python, Java
- **라이브러리**는 필요한 기능을 가져다 쓰는 코드 모음입니다. 예: React
- **프레임워크**는 애플리케이션의 기본 구조와 실행 흐름을 제공하는 틀입니다. 예: Next.js, Django
- **런타임**은 프로그램을 실제로 실행하는 환경입니다. 예: 브라우저, Node.js

비유하면 언어는 글을 쓰는 언어, 라이브러리는 참고할 수 있는 도구 상자, 프레임워크는 작업 순서가 정해진 공방, 런타임은 작업을 실제로 수행하는 작업장과 같습니다.

### 웹 언어의 흐름

- **HTML**은 페이지의 구조와 의미를 나타냅니다. 제목, 문단, 링크, 입력창 같은 요소를 작성합니다.
- **CSS**는 색상, 간격, 배치, 반응형 화면 등 표현을 담당합니다.
- **JavaScript**는 버튼 클릭, 데이터 요청, 화면 갱신처럼 동적인 동작을 담당합니다.
- **TypeScript**는 JavaScript에 타입 검사를 더해, 데이터의 형태가 맞지 않는 실수를 개발 중에 발견하도록 돕습니다. 브라우저나 Node.js에서 실행되기 전 JavaScript로 변환됩니다.

초기 웹은 HTML로 문서를 보여주는 데서 출발했고, CSS로 표현을 분리했으며, JavaScript가 더해지면서 사용자 입력에 반응하는 애플리케이션으로 발전했습니다. 이후 React 같은 UI 라이브러리와 Next.js 같은 프레임워크가 복잡한 화면과 라우팅, 서버 렌더링을 체계적으로 다루게 해주었습니다.

### 버전 번호 읽기

많은 소프트웨어는 `주버전.부버전.수정버전` 형태를 사용합니다. 예를 들어 `4.2.1`에서 첫 번째 숫자는 큰 변화, 두 번째 숫자는 기능 추가, 세 번째 숫자는 호환성을 유지하는 버그 수정을 나타내는 경우가 많습니다. 다만 정확한 정책은 기술마다 다르므로 공식 릴리스 노트를 확인하세요.

- **LTS(Long-Term Support)**: 비교적 긴 기간 보안·안정성 업데이트를 제공하는 릴리스
- **최신 버전**: 새 기능이 먼저 들어갈 수 있지만, 프로젝트의 의존성이나 운영 환경과 호환되는지 확인해야 함
- **버전 고정**: 팀원과 배포 환경에서 같은 도구 버전을 사용하도록 버전을 기록하는 것

버전 번호가 높다는 이유만으로 무조건 올리기보다는, 지원 기간과 호환성, 변경 내역을 확인하고 테스트한 뒤 업그레이드하는 것이 안전합니다. 특정 시점의 최신 버전은 빠르게 바뀌므로 공식 사이트의 지원 정책을 확인하세요.

## 3. 프론트엔드

**프론트엔드(frontend)**는 사용자가 브라우저나 앱에서 직접 보고 조작하는 부분입니다. 화면을 표시하고, 입력을 받고, 서버의 데이터를 사용자에게 이해하기 쉽게 보여줍니다.

### 기본 구성

- **HTML**: 콘텐츠의 구조와 의미
- **CSS**: 색, 크기, 배치, 반응형 스타일
- **JavaScript / TypeScript**: 사용자 동작과 데이터 처리
- **UI 라이브러리·프레임워크**: 화면을 컴포넌트 단위로 만들고 상태를 관리

### 자주 쓰는 기술

| 기술 | 역할 | 이런 경우에 잘 맞음 |
|---|---|---|
| React | 컴포넌트 기반 사용자 인터페이스 라이브러리 | 다양한 웹 화면을 조합하고 생태계를 활용할 때 |
| Next.js | React 기반 웹 프레임워크. 라우팅, 서버 렌더링 등 제공 | 공개 페이지, 검색 노출, 서버 기능이 함께 필요한 웹 서비스 |
| Vue | 컴포넌트 기반 UI 프레임워크 | 점진적으로 도입하거나 단순한 학습 곡선을 선호할 때 |
| Angular | 기능과 구조가 폭넓게 갖춰진 프레임워크 | 규모가 크고 정해진 구조와 도구를 원하는 팀 |
| Vite | 개발 서버와 번들링 도구 | 빠른 개발 환경으로 SPA를 만들거나 프론트엔드 도구를 구성할 때 |

React와 Vue는 UI를 만드는 도구이며, Next.js는 React 애플리케이션을 구성하는 프레임워크입니다. Vite는 그 자체로 UI 프레임워크가 아니라 개발·빌드 도구예요.

### SPA와 서버 렌더링

- **SPA(Single-Page Application)**: 브라우저가 JavaScript를 실행해 화면을 구성하고, 화면 전환 시 필요한 데이터만 바꾸는 방식입니다. 로그인 뒤 관리 도구처럼 앱 안에서의 상호작용이 많은 서비스에 적합할 수 있습니다.
- **SSR(Server-Side Rendering)**: 서버가 요청에 맞는 HTML을 만들어 브라우저로 보내는 방식입니다. 첫 화면 표시나 검색 엔진이 읽을 콘텐츠가 중요한 페이지에 유용할 수 있습니다.
- **SSG(Static Site Generation)**: 빌드 시점에 HTML을 미리 생성하는 방식입니다. 내용 변경이 드물고 빠르게 제공할 수 있는 문서·소개 페이지에 적합할 수 있습니다.

실제 프레임워크는 이 방식들을 조합해서 사용할 수 있습니다. 검색 노출이나 초기 표시 속도는 렌더링 방식뿐 아니라 콘텐츠, 캐시, 이미지 크기, 네트워크 등 여러 요소의 영향을 받습니다.

### 프론트엔드에서 함께 고려하는 것

- **라우팅**: URL과 화면을 연결합니다.
- **상태 관리**: 로그인 상태, 폼 입력, 서버 데이터 등 화면의 상태를 관리합니다.
- **폼과 검증**: 사용자가 입력한 값을 확인하고 이해하기 쉬운 오류를 알려줍니다.
- **접근성**: 키보드와 보조 기술을 포함해 다양한 사용자가 이용할 수 있게 합니다.
- **성능**: 필요한 코드만 불러오고 이미지와 데이터를 적절히 최적화합니다.

## 4. 백엔드

**백엔드(backend)**는 브라우저 화면 뒤에서 요청을 처리하는 부분입니다. 권한 확인, 비즈니스 규칙 적용, 데이터 읽기·쓰기, 외부 서비스 연동 등을 담당합니다.

### 일반적인 요청 흐름

```text
브라우저 → HTTP 요청 → 서버가 입력·권한 확인 → 데이터베이스 조회/수정 → HTTP 응답 → 화면 갱신
```

예를 들어 사용자가 프로필 저장을 누르면, 브라우저가 서버에 내용을 보내고 서버는 로그인 여부와 입력값을 확인한 뒤 데이터베이스에 저장합니다. 브라우저에서 숨겨 둔 버튼만으로 권한을 보호할 수는 없으므로, 서버와 데이터베이스에서도 권한을 확인해야 합니다.

### 백엔드 기술 선택지

| 기술 | 설명 | 선택을 고려할 상황 |
|---|---|---|
| Node.js | JavaScript/TypeScript를 서버에서 실행하는 런타임 | 프론트엔드와 언어를 공유하거나 입출력 중심 API를 만들 때 |
| Express | Node.js용으로 널리 쓰이는 웹 프레임워크 | 필요한 구조를 작게 시작하고 자유롭게 선택하고 싶을 때 |
| NestJS | 모듈과 의존성 주입 등 구조를 제공하는 Node.js 프레임워크 | 팀 단위로 일관된 서버 구조와 규칙이 필요할 때 |
| Python + Django | 관리 기능과 여러 웹 구성 요소를 제공하는 프레임워크 | Python 생태계와 빠른 CRUD 개발이 중요한 경우 |
| Python + FastAPI | 타입 힌트와 API 문서 지원이 강한 프레임워크 | Python으로 API를 만들고 요청·응답 스키마를 명확히 할 때 |
| Java + Spring Boot | 기업 환경에서 널리 쓰이는 서버 프레임워크 | 대규모 서비스와 성숙한 Java 생태계가 필요한 경우 |

### API와 배포 형태

- **REST API**는 URL과 HTTP 메서드(GET, POST, PUT, DELETE 등)를 사용해 리소스를 다루는 방식입니다.
- **GraphQL**은 클라이언트가 필요한 데이터 모양을 질의하는 API 방식입니다. 유연한 조회가 유용하지만 서버 설계와 캐싱을 함께 고려해야 합니다.
- **BFF(Backend For Frontend)**는 특정 프론트엔드에 맞춘 서버 계층입니다. 화면에 필요한 데이터를 모으거나 비밀 키를 안전하게 다루는 데 쓸 수 있습니다.
- **서버리스 함수**는 요청이 있을 때 실행되는 관리형 함수입니다. 서버 운영 부담을 줄일 수 있지만 실행 시간, 비용, 플랫폼 제약을 살펴야 합니다.

서버를 직접 만들지 않고 관리형 인증·데이터베이스 서비스를 이용할 수도 있습니다. 다만 관리형 서비스도 권한 정책, 비밀 값, 백업, 비용과 서비스 종속성을 검토해야 합니다.

## 5. 데이터베이스

**데이터베이스(Database, DB)**는 서비스가 사용하는 정보를 구조적으로 저장하고 필요할 때 조회·수정하는 시스템입니다. 사용자, 상품, 주문, 게시글처럼 오래 보존해야 하는 데이터가 대표적입니다.

### 관계형 데이터베이스와 SQL

관계형 데이터베이스는 데이터를 표(table)와 행(row), 열(column)로 구성하고, SQL로 조회·수정합니다.

| 데이터베이스 | 특징 | 고려할 점 |
|---|---|---|
| PostgreSQL | 기능이 풍부한 오픈소스 관계형 DB | 복잡한 관계·제약조건·트랜잭션을 다루기 좋음 |
| MySQL | 널리 사용되는 관계형 DB | 웹 서비스와 관리형 호스팅 선택지가 많음 |
| SQLite | 파일 하나로 시작할 수 있는 관계형 DB | 로컬 앱, 테스트, 작은 서비스에 간편하지만 동시 쓰기와 운영 요구를 살펴야 함 |

SQL의 기본 동작은 `SELECT`(조회), `INSERT`(추가), `UPDATE`(수정), `DELETE`(삭제)입니다. 테이블 간 관계는 외래 키로 표현하고, 제약 조건으로 허용되는 데이터 형태를 제한할 수 있습니다.

### NoSQL 데이터베이스

NoSQL은 관계형 표 구조만으로 표현하기 어려운 데이터나 접근 패턴을 다루는 데이터베이스 범주입니다. 문서형, 키-값형, 그래프형 등 종류가 다양합니다.

- **문서형 DB**: JSON과 비슷한 문서 단위로 데이터를 저장합니다.
- **키-값 DB**: 키를 통해 값을 빠르게 찾는 방식으로 캐시 등에 활용됩니다.
- NoSQL이라고 해서 스키마나 데이터 모델링이 필요 없는 것은 아닙니다. 어떤 조회가 필요한지 먼저 설계해야 합니다.

### 데이터 일관성과 보안

- **트랜잭션**은 여러 데이터 변경을 한 묶음으로 처리해, 모두 성공하거나 모두 취소되도록 합니다.
- **인덱스**는 자주 찾는 데이터를 빠르게 조회하도록 돕지만, 지나치게 만들면 저장 공간과 쓰기 성능에 부담이 됩니다.
- **마이그레이션**은 테이블이나 컬럼 변경을 파일로 기록하고 순서대로 적용하는 방법입니다. 팀과 환경 간 데이터베이스 구조를 맞추는 데 중요합니다.
- **백업과 복구**는 장애나 실수로 데이터가 사라졌을 때 복구하기 위한 운영 계획입니다.
- **권한 정책**은 사용자가 접근할 수 있는 데이터와 작업을 제한합니다. 애플리케이션 서버와 DB 모두에서 필요한 검사를 해야 합니다.

### 관리형 데이터 서비스

Supabase 같은 서비스는 PostgreSQL을 기반으로 데이터베이스, 인증, 파일 저장 등의 기능을 관리형으로 제공합니다. 개발과 운영을 단순하게 시작할 수 있지만, 데이터베이스 권한 정책과 키 관리 책임까지 사라지는 것은 아닙니다. 공개용 키와 서버 전용 비밀 키를 구분하고, 비밀 키를 브라우저 코드에 포함하지 않아야 합니다.

## 6. 프로젝트 유형별 추천 스택

아래는 출발점으로 삼을 수 있는 예시입니다. 최종 선택은 팀의 경험, 배포 환경, 보안·성능 요구에 맞춰 조정하세요.

| 프로젝트 유형 | 시작하기 좋은 조합 예시 | 선택 이유와 주의점 |
|---|---|---|
| 정적 포트폴리오·개인 블로그 | HTML/CSS/JavaScript 또는 React 기반 정적 사이트 도구 | 콘텐츠 위주라 서버를 최소화할 수 있습니다. 접근성과 콘텐츠 관리도 고려하세요. |
| 검색 노출이 중요한 공개 웹 | TypeScript + React/Next.js + 관리형 SQL DB | 서버 렌더링·정적 생성을 선택할 수 있습니다. SEO 결과는 콘텐츠와 성능 전반에 달려 있습니다. |
| 로그인 뒤 관리자 대시보드 | React + TypeScript + Vite + API 서버 또는 관리형 백엔드 | SPA로 빠르게 구성할 수 있습니다. API와 DB에서 인증·인가를 반드시 검증해야 합니다. |
| 간단한 CRUD 웹 서비스 | Next.js 또는 React + Node.js + PostgreSQL | 한 언어 생태계로 시작할 수 있습니다. 데이터 관계와 마이그레이션을 초기에 정리하세요. |
| 데이터 분석·자동화 도구 | Python + Jupyter 또는 FastAPI | 데이터·과학 생태계를 활용하기 좋습니다. 배포용 API와 분석 노트북의 역할을 구분하세요. |
| 모바일 앱 | React Native 또는 Flutter + API/관리형 백엔드 | 코드 공유 범위와 네이티브 기능, 앱스토어 배포 요구를 비교하세요. |
| 실시간 협업·채팅 | 프론트엔드 + WebSocket/실시간 서비스 + 영속 DB | 연결 관리, 메시지 순서, 재접속, 남용 방지와 비용을 함께 설계해야 합니다. |

### 간단한 선택 순서

1. 사용자가 누구이고 어떤 화면을 쓰는지 적습니다.
2. 검색 노출, 실시간 처리, 파일 업로드, 권한 분리 등 필수 요구를 정합니다.
3. 팀이 운영할 수 있는 가장 단순한 구조부터 검토합니다.
4. 작은 기능으로 기술 조합을 시험하고 배포까지 해봅니다.
5. 병목이나 요구가 확인되면 그때 필요한 부분만 확장합니다.

처음부터 대규모 서비스용 구성을 모두 도입할 필요는 없습니다. 단순하게 시작하되, 데이터와 권한을 안전하게 다루고 나중에 바꿀 수 있도록 기록을 남기는 것이 좋습니다.

## 7. 핵심 비교표

| 구분 | 선택지 A | 선택지 B | 빠른 판단 기준 |
|---|---|---|---|
| 언어 | JavaScript | TypeScript | 빠르게 문법에 익숙해지고 싶으면 JavaScript부터, 팀 코드의 데이터 형태를 점검하고 싶으면 TypeScript |
| UI | React | Vue | 팀 경험, 생태계, 프로젝트 구조 선호를 비교 |
| React 개발 도구 | Vite | Next.js | SPA 중심이면 Vite가 단순할 수 있고, 라우팅·서버 렌더링·서버 기능이 필요하면 Next.js 검토 |
| API 구조 | REST | GraphQL | 명확한 리소스 API는 REST가 단순할 수 있고, 화면별로 필요한 데이터 조합이 다양하면 GraphQL 검토 |
| DB | 관계형 SQL | NoSQL | 관계·트랜잭션·제약조건이 중요하면 SQL, 데이터 접근 패턴과 문서형 구조가 맞으면 NoSQL 검토 |
| 호스팅 | 관리형 플랫폼 | 직접 클라우드 구성 | 운영 인력이 적으면 관리형이 편리하고, 높은 제어가 필요하면 직접 구성을 검토 |
| 저장소 구조 | 모노레포 | 멀티레포 | 앱 간 코드 공유와 일괄 변경이 많으면 모노레포, 권한·배포·팀 경계를 강하게 분리해야 하면 멀티레포 검토 |

비교표는 절대적인 우열을 뜻하지 않습니다. 예를 들어 Next.js에서도 SPA와 비슷한 상호작용 화면을 만들 수 있고, SQL 데이터베이스도 JSON 형태의 데이터를 저장할 수 있습니다. 이름만 보고 결정하기보다 필요한 기능과 운영 조건으로 판단하세요.

## 8. 초보자 학습 로드맵

### 1단계: 웹의 기초

HTML로 의미 있는 문서 구조를 만들고, CSS로 배치와 반응형 레이아웃을 익힙니다. 브라우저 개발자 도구를 사용해 요소와 네트워크 요청을 확인하는 습관도 들이세요.

### 2단계: JavaScript 기초

변수, 함수, 배열·객체, 조건문, 반복문, 모듈을 배웁니다. 비동기 처리와 `fetch`로 API를 호출해 보고, 입력값과 오류를 다뤄보세요.

### 3단계: Git과 작은 프로젝트

Git으로 변경 이력을 관리하고, 작은 웹 페이지를 만들어 배포합니다. 기능을 잘게 나누고 README에 실행 방법을 기록해 보세요.

### 4단계: TypeScript와 컴포넌트

JavaScript 기초가 익숙해지면 타입, 함수 매개변수, 객체 타입, 유니언 타입을 배웁니다. React를 선택했다면 컴포넌트, props, state, 이벤트와 폼을 순서대로 익힙니다.

### 5단계: API와 데이터베이스

HTTP 요청·응답, 상태 코드, JSON을 이해하고 작은 API를 호출하거나 만듭니다. SQL의 기본 조회·추가·수정·삭제, 테이블 관계, 제약 조건을 연습하세요.

### 6단계: 인증·인가와 보안 기초

로그인(인증)과 권한 확인(인가)을 구분합니다. 브라우저에 비밀 키를 넣지 않고, 서버에서 입력과 권한을 검증하는 이유를 익히세요. 실제 사용자 데이터로 연습하지 말고 안전한 테스트 환경을 사용하세요.

### 7단계: 테스트와 배포

빌드, 린트, 타입 검사, 기본 테스트를 실행하고, 환경 변수와 개발·운영 환경의 차이를 이해합니다. 배포 후 로그와 오류를 확인하는 과정까지 경험합니다.

### 8단계: 필요한 전문 분야로 확장

검색 노출, 접근성, 성능 최적화, 캐싱, 모니터링, CI/CD, 모바일 개발 등 실제 프로젝트 요구에 맞춰 깊이를 더합니다. 한 번에 모든 기술을 배우기보다는, 작동하는 작은 서비스를 완성하고 다음 문제를 해결하며 확장하세요.

### 学습할 때 기억할 점

- 문법을 외우는 것보다 작은 기능을 직접 만들고 설명해 보는 것이 효과적입니다.
- 공식 문서와 릴리스 노트를 확인하고, 오래된 튜토리얼의 버전과 현재 도구가 맞는지 살펴보세요.
- 오류가 나면 전체 메시지와 재현 단계를 기록하고, 한 번에 하나씩 원인을 좁히세요.
- 기술 선택 이유와 포기한 대안을 짧게 기록하면 다음 프로젝트에서 더 나은 결정을 내릴 수 있습니다.
